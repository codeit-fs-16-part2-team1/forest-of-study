# 공부의 숲 API 작업

## 작업 기준

- [AGENTS.md](../../../AGENTS.md)에서 작업 권한과 승인 범위를 확인한다. 터미널·Git·설치·서버·DB·migration·테스트를 실행하지 않는다. 다른 도구로 셸 실행을 우회하지 않는다. 파일은 허용된 전용 도구로 읽고 편집한다.
- [README.md](../../../README.md)의 기능 범위, [API.md](../../../docs/API.md)의 담당 API 계약, [issues.md](../../../docs/issues.md)의 선행·완료 기준을 읽는다. DB 변경은 [DB.md](../../../docs/DB.md), [schema.prisma](../../../api/prisma/schema.prisma), 기존 migration을 함께 대조한다.
- [ADR.md](../../../docs/ADR.md)의 현재 적용 기준과 대체 관계를 확인한다. 폐기된 토큰·Heartbeat·초기화 보상을 복원하지 않는다. 해결되지 않은 충돌은 질문하고 명세를 임의로 고쳐 구현에 맞추지 않는다.
- 기존 코드가 명세와 다르면 후속 구현 과제로 구분한다. 승인 범위 밖의 인증·조회 정책 변경을 리팩토링에 섞지 않는다.
- 실제 의존성·명령은 [api/package.json](../../../api/package.json)을 확인한다. 새 도구·라이브러리 도입은 별도 승인이 필요하며 Vitest는 ADR-061에 따라 사용하지 않는다.

## 구현과 검토

1. 이슈·기능/API ID와 요청·응답·인증·오류·DB 반영 조건을 확인한다. 바꿀 파일과 사람이 확인할 방법을 계획하고 AGENTS.md와 현재 사용자 지시의 승인 절차를 따른다. 이미 승인된 작업은 같은 승인을 반복 요청하지 않는다.
2. 스키마는 입력 검사·정리, 미들웨어는 공통 인증·오류, 라우트는 검사·서비스 호출·응답, 서비스는 DB 조회와 업무 처리로 역할을 나눈다. 기존 구조를 옮길 때 URL과 외부 동작을 보존한다.
3. [API 규칙](references/apiRules.md) 중 해당 영역을 적용한다. 공통 UUID·오류·응답 함수는 실제 export와 호출 규약을 읽고 재사용한다.
4. 모델·제약 변경이 필요한 경우 작성된 migration과 실제 적용 여부를 구분한다. 적용된 SQL 이력을 임의로 덮어쓰거나 데이터 삭제로 문제를 숨기지 않는다.
5. 변경 파일과 주요 내용, 사람이 실행할 명령의 작업 디렉터리·선행 조건, api.http 요청/API ID·예상 상태 코드와 DB 결과를 전달한다. 실제 실행한 결과와 미실행 검증을 구분한다.

## JavaScript와 파일명

- 함수는 화살표 함수, 모듈은 ESM import/export, API 파일은 camelCase를 사용한다.
- 이름 변경 시 정적 import, 동적 import(), package.json 스크립트, 검사 스크립트와 실행 안내의 참조를 함께 확인한다.
- API URL의 kebab-case, Prisma 모델의 PascalCase, migration 식별자·도구의 고정 파일명은 별도 규칙이다. 파일명 통일을 이유로 변경하지 않는다.

## 검증 경계

- 파일 검토만으로 문법 검사·테스트·DB 제약 적용이 성공했다고 보고하지 않는다.
- .env 및 .env.*를 읽거나 출력하지 않는다. 연결 정보는 필요한 변수 이름과 설정 방법만 안내한다.
- DB를 변경하는 검증은 스크립트의 대상 제한을 먼저 검토한다. DB 없는 규칙 검사·로컬 API 검증·배포 환경 수동 확인을 구분한다. 사용자에게서 실행 결과를 받은 경우 그 환경과 범위를 근거로 기록한다.
