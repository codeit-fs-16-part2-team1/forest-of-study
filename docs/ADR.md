## ADR-001 — 프로젝트 기술과 작업 조건

- 날짜: 2026-10-08
- 상태: 확정
- 결정:

  - React(JavaScript)·React Router·axios / Express 5·Prisma 7·PostgreSQL을 사용하고 Netlify·Render·Neon에 배포한다.
  - 비밀번호는 bcrypt로 저장하며 로그인·파일 업로드·TypeScript는 제외한다.
  - 추가 의존성은 ADR-017을 따른다.
  - 설계와 구현은 별도로 검토한다.

- 이유: 기술과 범위를 고정해 3명·10일 일정의 환경 설정과 학습 비용을 줄인다.
- 다시 볼 때: 팀 규모·일정·배포 환경이 바뀔 때.

## ADR-052 — Challenge 축소와 브라우저 종료 후 계속 진행

- 날짜: 2026-10-12
- 상태: 확정
- 결정:

  - 모델: Challenge는 id·studyId·goalMinutes·status·elapsedMilliseconds·lastStartedAt·awardedPoints·createdAt의 8개 컬럼으로 관리한다. 상태는 RUNNING·PAUSED·RESET·COMPLETED다.
  - 단일 활성: RUNNING·PAUSED 합계는 스터디당 1개다. 일시정지된 집중이 있으면 새 집중을 시작하지 않고 기존 집중을 재개하거나 초기화한다.
  - 시간 계산: elapsedMilliseconds는 이전 실행 구간의 누적값, lastStartedAt은 현재 실행 구간의 시작 시각이다. RUNNING에만 서버 현재 시각 차를 더하고 목표 길이로 제한하며 정지 시간은 제외한다.
  - 이탈·복원: 브라우저 종료·외부 이동 중에도 RUNNING은 계속 진행하고 PAUSED는 수동 재개까지 유지한다. 내부 이동·새로고침 후에도 서버 데이터로 복원한다.
  - 초기화: PAUSED 행을 지급 없이 RESET으로 종료해 보존한다. 화면은 원래 목표·경과 0의 시작 전 상태로 돌아가고 다음 Start에서 새 행을 만든다.
  - 다른 브라우저: 비밀번호를 알면 기존 집중을 조작할 수 있다. 여러 브라우저의 요청 순서 충돌 처리는 제외하되 단일 활성과 완료 중복 지급 방지는 유지한다.
  - 제외 범위: 토큰·타이머 키·브라우저 소유권·Heartbeat·연결 만료·자동 일시정지·담당 탭 인계·stateVersion은 사용하지 않는다.
  - API: 조회는 종료·지급을 수행하지 않는다. 이탈 중 목표를 채운 경우 복귀 후 보호 요청 검증과 완료 요청으로 지급한다. API-FC-07·API-AU-02는 폐기하고 ID를 재사용하지 않는다. 비밀번호 유지 범위는 ADR-073을 따른다.

- 이유: 시간 복원에 필요한 상태만 저장해 브라우저 연결 감지와 소유권 관리 비용을 줄인다.
- 다시 볼 때: 자동 정지·다중 브라우저 제어·집중 상태를 확장할 때.

## ADR-053 — 완료 전용 지급과 Challenge.awardedPoints

- 날짜: 2026-10-12
- 상태: 확정
- 결정:

  - 지급: 목표 완료에만 floor(goalMinutes/10)+3P를 지급하며 상한은 없다. 10·20·25·180분 완료는 각각 4·5·5·21P다. 정지·재개·초기화·부분 경과에는 지급하지 않는다.
  - 저장: PointHistory·PointKind를 사용하지 않고 Challenge.awardedPoints에 집중별 지급량, Study.points에 총점을 저장한다. 전체 모델은 5개·Cascade 관계는 4개다.
  - 원자성: 서버 시간으로 목표 도달을 검증하고 RUNNING/PAUSED → COMPLETED 조건부 전환·지급량 기록·총점 증가를 같은 트랜잭션으로 처리한다. 전환에 성공한 요청만 지급하고 실패 시 전부 롤백한다.
  - 재요청: 같은 완료 재요청은 200·신규 0P이며 기존 지급량과 총점은 보존한다.

- 이유: 지급 시점을 하나로 모으고 재요청·동시 완료의 중복 지급을 막는다.
- 다시 볼 때: 지급식·보상 시점·지급 이력 구조를 변경할 때.

## ADR-054 — DB와 API의 도메인 용어 통일

- 날짜: 2026-10-12
- 상태: 확정
- 결정:

  - 명칭: DB·API는 Routine·RoutineHistory·Challenge·Reaction을 공통 사용한다. JSON 필드는 DB 컬럼과 같은 camelCase, 컬렉션 경로는 복수형 kebab-case로 작성한다.
  - 시간: 현재 집중 조회는 /studies/{studyId}/challenges/current다. elapsedMilliseconds·lastStartedAt·createdAt은 저장 의미 그대로 전달하고 실제 경과 초는 elapsedSeconds로 별도 계산한다. 저장 누적값을 조회 시 계산값으로 덮어쓰지 않는다.
  - 호환 범위: 이전 API 별칭은 지원하지 않는다. 기존 기능·API 추적 ID와 여섯 화면 주소는 유지하며 세부 경로·필드는 API.md를 따른다.

- 이유: 계층 간 이름 변환과 잘못된 필드 연결을 줄인다.
- 다시 볼 때: 도메인 명칭이나 API 버전을 변경할 때.

  - 목록 기본값: offset=0·limit=6·sort=latest를 사용한다. limit 상한은 ADR-064를 따른다.
  - 검색: name·nickname·introduction의 OR 부분 검색을 사용한다. 검색어는 trim·NFC, 대상 문자열은 NFC로 정규화하고 대소문자는 구분하지 않는다. %·_는 일반 문자이며 trim 후 빈 검색어는 필터 없이 조회한다.

- 이유: 입력 실수를 드러내고 화면과 서버의 검색 결과를 일치시킨다.
- 다시 볼 때: 쿼리 확장·검색 방식·목록 기본값을 바꿀 때.

## ADR-060 — 현재 코드 기준 주간 기록 계약

- 날짜: 2026-10-15
- 상태: 부분 대체: ADR-074·ADR-080
- 결정:

  - 기간: weekStart는 필수이며 해당 날짜가 속한 주의 월요일로 보정해 월~일 7일을 조회한다. 과거·미래 제한은 없지만 유효 날짜와 보정 후 7일의 YYYY-MM-DD 표현 범위를 검사한다.

- 다시 볼 때: 주 시작일·조회 기간·기록표 응답을 변경할 때.

## ADR-063 — 다건 조회는 중복 제거 후 최대 10개

- 날짜: 2026-10-15
- 상태: 확정

## ADR-064 — 진행 일수·최근 조회·중복 조합·목록 상한·응원 동일성

- 날짜: 2026-10-15
- 상태: 부분 대체: ADR-078 (최근 조회)
- 결정:

  - 진행 일수: 스터디 생성 당일을 1일째로 표시한다.
  - 최근 조회 대신 북마크를 사용하며 등록·해제·순서 기준은 ADR-078을 따른다.
  - 목록 개수: limit은 기본 6·최대 6이며 더보기는 6개씩 조회한다. 북마크 UI 3개·목록 API 최대 6개·ID 다건 API의 서로 다른 ID 최대 10개는 각각 별도의 제한이다.
  - 스터디 중복: trim 후 nickname/name 조합에만 @@unique([nickname,name])를 적용하고 생성·수정 충돌은 409 STUDY_CONFLICT로 처리한다. nickname·name 각각에는 UNIQUE를 적용하지 않으며 대소문자·Unicode 표현을 새로 합치는 정책은 추가하지 않는다.
  - 응원 동일성: 모든 이모지를 허용한다. Reaction.emoji에서 피부색 수정자 U+1F3FB~U+1F3FF를 제거한 기본 이모지로 저장·표시·중복 검사·집계한다. 👍·👍🏽·👍🏻는 👍로 표시하고 같은 브라우저의 중복 반응으로 취급하며 다른 브라우저의 반응은 각각 집계한다. 별도 색상 컬럼·응원 정규화 테이블은 만들지 않는다.
  - 기존 데이터: 중복 Study나 피부색별 Reaction의 전환 정책은 별도 검토하며 기존 데이터를 임의로 삭제하지 않는다.
  - 배경: 총 8종의 키와 기본값은 유지하고 실제 색상·이미지는 추후 지정한다.

- 이유:

  - 진행 일수: 스터디의 시작일을 자연스럽게 표시한다.
  - 목록·중복: 카드 표시와 요청 크기를 맞추고 같은 닉네임·이름 조합의 혼동을 줄인다.
  - 응원: 피부색 때문에 같은 의미의 반응과 중복 기준이 나뉘지 않게 한다.
  - 배경: 키·기본값을 유지하면서 실제 자산을 함께 확정한다.

- 다시 볼 때:

  - 표시 개수·진행 일수·스터디 동일성 기준을 변경할 때.
  - 응원 정규화나 기존 데이터 전환을 적용할 때.
  - 배경 색상·이미지를 지정하거나 변경할 때.

## ADR-065 — Header·모달·시간 입력·기록표 색상·화면 상태

- 날짜: 2026-10-15
- 상태: 부분 대체: ADR-070·ADR-074·ADR-080
- 결정:

  - Header: 스터디 만들기 버튼은 홈(`/`)에서만 PC·태블릿·모바일 모두에 표시한다. 로고의 홈 이동 규칙은 유지한다. 고정 Header와 본문 여백은 ADR-067을 따른다.
  - 모달: 일반 모달은 배경 클릭·나가기·취소로 닫고 URL을 유지한다. 내부 클릭으로는 닫지 않으며 Escape로도 닫지 않는다. 이미 보낸 API 요청의 취소 기능은 추가하지 않는다. 비밀번호 모달의 취소 이동은 ADR-070을 따른다.
  - 시간 입력: 집중 시간 변경은 모달로 제공한다. 타이머 숫자 자체를 input으로 바꾸는 방식은 검토 후보이며 현재 요구사항은 아니다.
  - 이모지 선택: emoji-picker-react의 기본 UI를 사용한다. 별도 선택창 설계나 외부 API 연동은 추가하지 않는다.
  - 기록표 색상·저장: ADR-074를 따른다. 존재 전 칸의 회색 규칙은 유지한다.
  - 기록표 정렬: 사용자 순서와 종료 행의 배치는 ADR-080을 따른다.
  - 화면 상태: 빈 목록·실패는 기존 시안, 완료는 시간 초과 시안을 사용한다. 시간 초과 시안을 사용하더라도 초과 경과·음수 타이머·추가 포인트를 도입하지 않는다. 로딩은 스켈레톤으로 표시하며 추후 변경할 수 있다.
  - 추가 자료: 반응형·습관 편집 시안은 ISS-003에서 추적한다. 스티커는 ADR-074의 기존 18종 자산을 사용한다. Header는 ISS-049, 모달은 ISS-050, 집중은 ISS-040·043, 주간표는 ISS-039, 공통 스타일은 ISS-025, 이모지 선택은 ISS-048에 적용한다.

- 이유:

  - 공통 UI: 생성 진입점·모달·시간 입력을 일관되게 제공하고 기존 선택기·시안을 재사용한다.
  - 미정 자료: 미전달 시안·색상은 구현자가 임의로 확정하지 않는다.

- 다시 볼 때:

  - 반응형·습관 편집 시안을 전달받거나 기존 발자국 자산을 변경할 때.
  - 모달·시간 입력·로딩 표현을 변경할 때.
  - 기록표 정렬이나 색상 저장 방식을 변경할 때.

## ADR-066 — 비밀번호 공백 포함 요청 거절

- 날짜: 2026-10-15
- 상태: 확정
- 결정:

  - 원문: 비밀번호·확인값은 문자열만 받으며 trim·공백 제거를 하지 않는다. 4~20자와 `/^[A-Za-z0-9!@#$%^&*]+$/`를 검사한다. 앞뒤·중간 스페이스·탭·줄바꿈 등 공백이 하나라도 있으면 400 VALIDATION_ERROR다.
  - 생성: 두 값 각각의 형식을 검사한 뒤 일치를 확인한다. 어느 한쪽의 공백·형식 오류는 400 VALIDATION_ERROR, 유효 형식인 두 값의 불일치는 400 PASSWORD_CONFIRM_MISMATCH다. 유효한 password 원문만 bcrypt로 해시한다.
  - 보호 요청: 진입 확인·삭제·보호 요청도 원문 형식 검사 후 bcrypt 비교한다. 누락은 401 VERIFICATION_REQUIRED, 유효 형식의 오답은 401 PASSWORD_MISMATCH를 유지한다.
  - 프론트·서버: 프론트는 공백 입력을 막고 붙여넣기도 검사하되 자동 삭제해 전송하지 않는다. 서버는 프론트 검사 여부와 관계없이 독립적으로 거절한다.

- 이유: 자동 보정으로 서로 다른 비밀번호가 같은 값으로 처리되지 않게 한다.
- 다시 볼 때: 허용 문자·길이·비밀번호 입력 정책을 변경할 때.

## ADR-074 — 습관별 발자국 색상 저장

- 날짜: 2026-10-21
- 상태: 부분 대체: ADR-080 (신규 기본 선택)
- 부분 대체: ADR-060의 주간 응답, ADR-065의 순서 기반 색상 배정·색상 미저장. 날짜·미완료/기간 밖 표시 규칙은 유지하며 정렬은 ADR-080을 따른다.
- 결정:

  - 발자국 버튼에서 기존18종 중 색상을 선택한다. 신규 항목의1번 자동 선택은 ADR-080을 따른다.
  - 습관 간 같은 색상 선택을 허용한다. 선택한 색상을 습관에 저장하고 이후 체크된 기록에 사용한다.
  - 색상 변경은 과거 기록에도 적용한다. 현재 습관의 색상을 조회하며 이력마다 색상을 따로 저장하지 않는다.
  - 기존 습관의 null은 별도 변환 없이 표시 목록 전체의0 기준 행 index로 (index % 18) + 1번 색상을 순환 표시한다. 저장 색상이 있는 행도 index에 포함하고 사용자가 지정한1~18은 순서와 무관하게 유지한다. 이 계산은 표시용이며 null을1이나 다른 번호로 저장하지 않는다.
  - API·컬럼·검증·기존 데이터 처리의 상세 계약은 API.md 5~6절과 DB.md의 습관 스티커 색상 항목을 따른다.

- 이유: 사용자가 정한 색상으로 습관을 구별하고 동일 습관의 현재·과거 기록에 같은 색상을 적용한다.
- 다시 볼 때: 팔레트·기존 습관 호환 정책을 바꾸거나 날짜별 색상 이력을 별도로 보존할 때.

## ADR-076 — 스터디 사용자 지정 배경 색상·패턴

- 날짜: 2026-10-21
- 상태: 부분 대체: ADR-079 (선택 UI·패턴 종류·글자 표시)
- 배경: 기존 8종 선택에 사용자가 직접 지정한 배경 색상을 추가하기로 했다. 이미지 파일 업로드는 보류한다.
- 결정:

  - 기존 배경8종과 기본green을 유지하고 custom 배경 저장을 추가한다. 생성·수정 모두 지원하며 선택 UI는 ADR-079를 따른다.
  - backgroundKey=custom과 backgroundColor=#rrggbb를 저장하며 기존 배경은 backgroundColor=NULL이다. API 입력·응답은 API.md, NULL·조합 제약과 migration은 DB.md에서 관리한다.
  - custom 배경의 패턴 원본은 프로젝트 SVG로 관리하고 무늬색을 별도로 저장한다. 종류·표시 방식은 ADR-079를 따른다. 사용자 파일 업로드는 보류한다.
  - patternKey·patternColor를 함께 저장하거나 함께 비운다. 기존 배경으로 전환할 때 패턴도 비운다. 입력·응답·PATCH 기준은 API.md, 컬럼·제약·migration은 DB.md를 따른다.
  - ADR-057의 8종만 허용하던 배경 선택 범위를 확장한다. 기존 데이터·기본 배경·이미지 4종은 유지한다.

- 이유: 기존 배경을 보존하면서 사용자 지정 설정을 키와 색상으로 저장한다.
- 다시 볼 때: 배경 저장 방식이나 파일 업로드 범위를 변경할 때.

## ADR-078 — 최근 조회 대신 북마크

- 부분 대체: ADR-064의 최근 조회 자동 기록·재방문 재정렬. API-ST-08의 입력 순서·서로 다른ID 최대10개는 유지한다.
- 배경: 방문 이력 대신 사용자가 직접 등록한 스터디를 홈에서 다시 찾게 한다.

## ADR-079 — 파스텔 팔레트·패턴5종·자동 글자색

- 날짜: 2026-10-22 (기존 구현과 후속 정책 기록)
- 상태: 확정
- 대체: ADR-075의 글자색 직접 선택. ADR-076의 선택 UI·패턴3종·stroke는 부분 대체한다.
- 배경: 카드의 개성을 유지하면서 배경과 글자 표시를 일정한 범위로 맞춘다.
- 결정:
  - 기존8종에 파스텔12색을 제공한다. 팔레트 밖의 기존 저장 색상은 수정 화면에서 유지할 수 있고 서버 HEX 검증은 유지한다.
  - 패턴은 없음과 씨앗(dots)·잔물결(waves)·소프트 체크(stripes)·작은 잎(leaves)·페이퍼(paper)다. 기존3종 저장키는 보존하고 무늬색은 별도로 선택한다.
  - 글자색 직접 선택은 제공하지 않는다. custom 닉네임은 팔레트별 강조색, 나머지 제목·소개는 자동 대비색을 사용한다. 팔레트 밖의 닉네임은 자동 대비색이다. stroke·텍스트 배경 상자는 사용하지 않는다.
  - textColor API·컬럼은 호환을 위해 유지하고 프론트는 생성·수정에 null을 보낸다. 기존 저장값·migration을 삭제하거나 임의 변환하지 않는다. 세부 API·DB·표시는 해당 명세와 프론트 상수를 따른다. 이미지 파일 업로드는 보류한다.
- 이유: 제한된 팔레트와 자동 글자색으로 카드 꾸미기와 가독성을 함께 관리한다.
- 다시 볼 때: 팔레트·패턴·자동 대비 또는 글자색 직접 선택을 변경할 때.

## ADR-080 — 습관10개·사용자 순서·신규1번 발자국

- 날짜: 2026-10-22 (기존 구현과 이번 승인 반영)
- 상태: 확정
- 부분 대체: ADR-056의18개·생성일 정렬·순서 저장 제외, ADR-060·065의 기록표 정렬, ADR-074의 신규 색상 직접 선택 필수.
- 배경: 습관 편집의 화면 제한과 생성·색상·순서 저장 기준을 일치시킨다.
- 결정:
  - 신규 활성 한도는 스터디당10개이며 종료·이력은 제외한다. 프론트는10개부터 추가를 제한하고 API는 Study 잠금 안에서 검사한다. 기존11~18개는 자동 삭제하지 않고 편집·종료·재정렬을 허용하되 초과 상태에서 개수를 늘리지 않는다.
  - 신규 입력칸은1번 발자국을 자동 선택하고 저장 시 stickerColor:1을 전송한다.18종 중 변경·동일 색상 중복은 허용한다. API의 신규 색상 필수 검증·기존 null 호환·과거 기록 최신 색상 반영은 유지한다. 기존 null은 ADR-074의 전체 행 index 기반18색 순환을 사용하며 신규 기본색1로 대체하지 않는다. 편집 모달의 이미지·번호 안내·선택창 표시를 같은 기준으로 맞추고 사용자가 색상을 고르기 전에는 저장값을 유지한다.
  - Routine.position으로 순서를 저장하고 API-HB-06의 order로 생성·이름·색상·종료와 함께 원자적으로 반영한다. 오늘 목록은 position ASC → createdAt ASC → id ASC다.
  - 주간 표는 미종료 행을 같은 순서로 먼저, 종료 행을 endsOn DESC → createdAt ASC → id ASC로 뒤에 표시한다. 과거 주도 현재 순서를 사용한다. 날짜·기록은 보존한다. 요청·호환·오류·migration 상세는 API.md·DB.md를 따른다.
- 이유: 사용자가 정한 순서를 재조회 후에도 유지하고 신규 습관은 별도 색상 선택 없이 저장할 수 있게 한다.
- 다시 볼 때: 활성 한도·기존 초과 데이터 호환·정렬·신규 기본 색상이나 날짜별 순서 이력이 필요할 때.
