## 로컬 DB 개발 환경

2026-10-11 사용자 요청으로 첫 이슈 ISS-001을 **Neon 호스팅 전 로컬 PostgreSQL 실행 환경 설정**으로 변경했다(ADR-049). 기존 첫 이슈의 미정 정책 확인은 ISS-002로 배치하고, 기존 ISS-002~025는 ISS-003~026으로 한 번호씩 이동했다(ADR-050). 기능 36개는 유지한다.

- 설정 파일: [compose.yaml](compose.yaml). 이미지 `postgres:18` — PostgreSQL 18 계열 태그이며 18.6 고정이 아니다. 컨테이너 이름은 `forest-of-study-db`다.
- DB 이름·사용자: `forest-of-study` — 사용자가 수정한 Compose 설정을 따른다.
- 로컬 개발 전용 비밀번호: `forest-of-study-local`.
- 로컬 접속: `localhost:5435`, 컨테이너 내부 PostgreSQL 포트: `5432`. 포트 매핑은 `5435:5432`로, 바인딩을 루프백 주소로 제한하지 않는다.
- named volume `forest-of-study-data`를 `/var/lib/postgresql`에 연결한다. `pg_isready` healthcheck는 10초 간격·5초 제한·5회 재시도·시작 유예 10초다.
- 기존 `postgres_data` 볼륨의 데이터는 새 볼륨에 자동 이전되지 않는다. 기존 데이터를 사용할 경우 별도 이전이 필요하다. 초기 DB·사용자·비밀번호 설정은 빈 데이터 디렉터리를 초기화할 때 적용되며, 기존 볼륨의 계정을 자동 변경하지 않는다.
- Neon 배포 대상은 유지한다. 로컬 컨테이너 설정을 배포용 접속 정보로 사용하지 않는다.
- 현재 상태: 파일 작성 완료. Docker 실행·DB 접속·데이터 보존 검증은 사람이 실행할 단계로 남아 있다. `.env`는 열거나 수정하지 않았다.

Docker Desktop 실행 후 저장소 루트에서 사람이 순서대로 입력한다.

```sh
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose exec db psql -U forest-of-study -d forest-of-study -c "SELECT version(), current_database();"
```

기대 결과: 구성 검사 오류 없음, `db`가 healthy, PostgreSQL 18 계열·DB forest-of-study. 호스트에서 접속할 때는 `localhost:5435`를 사용한다. 별도 테스트 데이터를 만든 뒤 `docker compose restart db` 후 다시 조회해 보존을 확인한다. API가 아직 구현되지 않았으므로 이 이슈는 api.http 대신 Docker·DB 확인으로 검증한다.

## 프로젝트 조건

- 팀: 부트캠프 수강생 3명, 프로젝트 기간 10일.
- 1차 배포: 2026년 10월 16일 금요일까지 배포 주소에서 전반적인 모든 사용자 흐름이 처음부터 끝까지 동작한다.
- 프론트엔드: React(JavaScript), React Router, axios. 배포: Netlify.
- 백엔드: Express 5, Prisma 7, PostgreSQL. 배포: Render, Neon.
- 비밀번호가 필요한 기능은 bcrypt로 해시한 비밀번호를 저장한다.
- 로그인, 파일 업로드, TypeScript는 사용하지 않는다.
- 추가 사용 예정 라이브러리: emoji-picker-react. 그 밖의 라이브러리는 사용자가 직접 알린 것만 목록에 추가하며, 임의로 선정·추가하지 않는다(ADR-017). 현재는 문서만 작성한다.

## 기능 목록

### ID와 이용자 정의

- 기능 ID는 F-ST(스터디), F-HB(습관), F-FC(집중), F-AU(비밀번호)와 일련번호로 구성한다. 이후 화면·API·이슈에서 같은 ID를 참조하고 삭제한 ID는 재사용하지 않는다.
- 출처의 BR은 위 원문 참조번호, ADR은 [결정 기록](ADR.md)의 ID다.
- 방문자: 로그인 없이 서비스를 이용하는 사람.
- 확인 이용자: 서버 비밀번호 검증으로 발급된 해당 스터디의 유효 일반 토큰을 가진 사람. 토큰은 내부 이동·재접속에 공유하며 한국 자정 만료한다. 생성자 본인 여부를 별도로 식별하지 않는다.
- 타이머 이용자: 해당 집중의 유효한 타이머 전용 키를 가진 브라우저 이용자.
- 미정 사항은 별도 표에서 추적하며 임의로 확정하지 않는다.

### 화면 동작·입력 조건

- 로고·홈 버튼은 /. 생성·수정 성공은 해당 상세, 삭제 성공은 / 이동 후 에러토스트 형식의 성공 안내. 실패 시 페이지 유지.
- 자체 모달의 나가기/취소는 모달만 닫고 주소 유지. 요청 중간 취소 기능은 없다.
- 닉네임 필수 최대10, 스터디 이름 필수 최대15, 소개 필수 최대100. 비밀번호4~20·영문/숫자/!@#$%^&* 문자만 허용, 확인값 일치. 비밀번호 변경 제외.
- 배경은 원색4·이미지4, 기본 첫 초록색green. 나머지 키·이미지 자산은 추후 전달받는다. 업로드 없음.
- 카드 제목은 ‘닉네임’의 / ‘스터디 이름’ 형태, 소개는 한 줄 말줄임. 진행 일수는 생성일 기준이며 생성 당일0/1은 미정.
- 습관 목록은 길어지면 스크롤. 목록 수정에서 생성·수정 함께 제공, +로 빈 입력 영역 추가 가능하나 빈 값을 저장하지 않는다. 이름 최대20. 최대18개의 활성/전체 적용 범위는 미정.
- 습관 빈 상태: ‘아직 습관이 없어요 / 목록 수정을 눌러 습관을 생성해보세요’. 생성일 이전 기록 칸은 회색, 줄별 색상은 정해진 순서로 적용하며 색상표·행 순서는 추가 확인.
- 타이머 초기 숫자 클릭으로10~180분 정수 설정(기본10). RUNNING에서는 Start·초기화 비활성, PAUSED에서는 정지 비활성·Start로 재개·초기화 가능. 초기화는 경과 정산 후RESET 종료, 자동 재시작 없음.
- PAUSED 시간 폰트는 빨간색. 이전 ‘종료 임박 빨강’ 추정은 확정 정책으로 사용하지 않는다. 완료 뒤 새 시작도 새 행 생성.
- PC·태블릿·모바일 모두 지원. 별도 수정 폼·습관 편집·이모지·완료/실패/빈 목록의 남은 시안과 breakpoint는 구현 시 사용자와 확인한다.
- 장식 이미지는 CSS background-image, 이동은 React Router Link 등 실제 a로 렌더되는 수단, 동작은 button을 사용한다. 내부 이동에 전체 문서 재로드를 강제하지 않는다. reset.css 적용. SCSS 규칙은 도입 승인 후 적용하며 Sass 의존성을 임의 추가하지 않는다.

### 인증과 집중 복구

일반 토큰은 스터디별 LocalStorage 보관, 다음 한국 자정 만료다. 만료는 서버가 검사하고 유효하면 새로고침·재접속에도 유지한다. 삭제는 모달 비밀번호 재확인을 유지한다. 비밀번호 원문은 저장하지 않는다.

타이머 키는 LocalStorage에 보관하고 DB에는 해시만 저장한다. 활성 타이머 조회·Heartbeat·정지·재개·초기화·완료만 허용하며 일반 토큰 만료와 무관하다. 다른 브라우저 조작은 경고 후 차단한다. 비밀번호 재확인과 명시적 복구 선택으로 조작권을 옮기면 이전 키는 무효다. RESET/COMPLETED에서 키 폐기, 다음 집중에는 새 키 발급.

내부 페이지·탭 전환은 진행 유지. 스터디별 담당 탭 하나가15초마다 Heartbeat를 보낸다. 보조 탭 종료는 영향 없고 담당 탭 새로고침·종료 시 다른 탭이 인계한다. 종료 이벤트에서 정지 요청은 보내지 않는다. 마지막 확인 후90초 이상 연결이 끊기면 마지막 확인 시각 기준 PAUSED로 복구한다.90초 이내 새로고침·재연결은 진행 유지, 만료 뒤에는 자동 재개하지 않는다. 백그라운드 제한·절전·통신 단절에도 항상 진행한다고 보장하지 않는다.

23:50에30분 집중을 시작하면 일반 토큰은00:00 만료지만 타이머는00:20 완료·정산 가능하다. 자정을 넘긴 PAUSED도 키로 재개한다. 새 집중 시작·습관·수정은 만료됐다면 재인증한다.

### 습관 기록·포인트 기준

습관 종료일을 기록에 포함한다: startsOn <= 날짜 <= endsOn. 종료일null이면 이후에도 유효하다. 종료 즉시 목록에서 숨기고 조작 차단, 오늘 생성→체크→종료도 기록 유지. 주간 표에는 조회 주와 유효 기간이 겹치는 습관만 표시한다.

초기화·목표 종료에만 경과10분당1P, 목표 완료 추가3P.10/20/25/180분 완료는4/5/5/21P. 목표 초과분과 서로 다른 집중의10분 미만 나머지는 버린다.13분 초기화1P·다음17분 초기화1P는 합계2P. 정지·조회·Heartbeat에는 지급 없음. Study.points는 PointHistory 신규 지급과 같은 트랜잭션으로 갱신한다.

brief.md는 원문으로 보존한다. 포인트·인증·종료일 등 후속 사용자 변경은 ADR-043~048을 우선 적용하며 원문 준수 항목과 변경 항목을 구별한다.

## 범위와 우선순위 — MoSCoW·P0/P1/P2

### 분류 기준과 검토 상태

이 절은 사용자의 ‘좋아요’로 승인된 범위·우선순위 기준이다(ADR-024). 기존 기능 ID와 확정 동작을 유지한다. 우선순위가 낮다는 이유로 기능을 제외하거나 10월 16일 이후로 자동 연기하지 않는다.

- MoSCoW는 이번 프로젝트에서 필요한 정도를 구분한다.
- P0·P1·P2는 기능을 연결하고 검증할 순서를 구분한다. 장애 심각도 등급으로 사용하지 않는다.
- 2026-10-16 배포에서 전반적인 모든 사용자 흐름이 동작해야 한다(ADR-002). 따라서 현재 합의된 36개 기능은 모두 Must다.
- P0만 완료하면 배포 기준을 충족하는 것이 아니다. P1·P2도 위 날짜까지 동작해야 한다.
- 시안·세부 규칙 확인 대기는 기능 제외 사유가 아니다. API 계약에 필요한 규칙은 확인하고, 사용자가 구현 시 정하기로 한 표현·상태는 그때 결정한다.
- 일부 Must를 Should·Could로 조정하려면 기능 ID·영향·이유를 제시해 사용자와 별도 합의하고 ADR에 기록한다.

| MoSCoW | 한국어 범위 | 적용 기준 | 현재 분류 |
| --- | --- | --- | --- |
| Must have | 꼭 필요 | 원문 또는 사용자 확정 요구이며 합의된 전체 흐름을 충족하는 데 필요 | 기존 기능 36개 |
| Should have | 있으면 좋음 — 우선 검토 | 핵심 흐름은 유지되지만 가치가 높은 개선. 현재 확정 기능을 여기에 두려면 범위 재합의 필요 | 필수 이후 개선 후보는 아래 참조 |
| Could have | 있으면 좋음 — 여유 시 검토 | 합의된 요구를 충족한 뒤 여유가 있을 때 검토할 선택 개선 | 필수 이후 개선 후보는 아래 참조 |
| Won’t have this time | 이번엔 안 함 | 사용자가 이번 범위에서 명시적으로 제외한 기능·기술 | 아래 제외 표 |

| 우선순위 | 구현·통합 순서 | 기능 수 | 완료 시점 기준 |
| --- | --- | --- | --- |
| P0 | 생성→상세→비밀번호→습관 기록·집중 완료→결과 확인과 수정·삭제, 날짜·시간·권한 상태를 먼저 연결·검증 | 27 | 가장 먼저 연결하되 별도 날짜는 아직 정하지 않음 |
| P1 | 목록 탐색·재방문과 응원 흐름을 연결하고 필수 동작 통합 | 6 | P0 기반 위에 연결; 2026-10-16까지 완료 |
| P2 | 핵심 데이터 흐름과 의존성이 낮은 공유·진행 일수·현재 시간 표시 완성 | 3 | 독립 작업은 앞당길 수 있으며 2026-10-16까지 완료 |

순서는 의존성과 조기 검증 필요성을 기준으로 제안했다. 담당자·소요 시간·날짜 배정은 이슈 목록 단계에서 진행한다.

### 함께 충족해야 하는 조건

기능별 표 밖의 공통 조건도 해당 기능과 함께 완료한다. 별도 기능으로 중복 집계하지 않는다.

| 공통 조건 | MoSCoW | 우선 적용 순서 | 이유 |
| --- | --- | --- | --- |
| Netlify·Render·Neon 배포와 화면/API/DB 연결 | Must | P0부터 실제 배포 환경에 연결 | 전체 흐름의 배포 동작이 첫 배포 기준이다 |
| 자체 비밀번호 모달, bcrypt 해시 저장·검증, 일반 토큰 공유·자정 만료와 삭제 모달의 재확인 | Must | P0 | 보호 기능 전반의 전제다 |
| 입력 제한·기본 배경·성공 후 이동·실패 시 해당 페이지 유지·삭제 성공 토스트 | Must | 해당 기능과 같은 순서 | 확정한 이용 흐름의 일부다. 정확한 오류 문구·표현은 구현 시 결정 |
| PC·태블릿·모바일 지원 | Must | P0부터 사용 가능한 구조로 작성하고 P1에서 전체 흐름 점검 | 세 기기 지원이 확정됐다. 상세 전환 기준은 미정 |
| 과거 습관 기록 보존·한국 자정 경계·서버 기준 시간 복원 | Must | P0 | 데이터·시간 기준이 틀리면 결과가 달라진다 |
| 제공 시안과 빈 습관 목록 안내·목록 수정 진입 | Must | 해당 화면 연결 순서 | 시안과 확인된 빈 상태의 이용 흐름을 함께 충족해야 한다 |

### 있으면 좋음

킥오프의 배경 랜덤·외부 앱 공유·이전 주 이동 UI·습관 색상 직접 선택·삭제 전 추가 확인·현재 시각1분 자동 갱신은 필수 이후 선택 개선 후보로 둔다. 별도 구현 승인 없이 Must로 추가하지 않는다. 비밀번호 변경은 현재 Won’t 유지하며 도전하려면 범위를 재합의한다.

### 범위 변경 시 선택지

| 선택지 | 장점 | 단점 | 현재 상태 |
| --- | --- | --- | --- |
| 현재 확정한 36개를 모두 Must로 유지하고 P 순서로 진행 | 원문·시안·사용자 결정과 전체 흐름 배포 기준 유지 | 3명·10일 일정에서 기능 범위를 줄여 확보할 여유가 없음 | 이번 초안에 적용 |
| 일부를 Should·Could로 낮추고 배포 범위 재합의 | 일정 여유를 확보하고 핵심 흐름에 더 집중 가능 | 원문 또는 확정 기능 일부가 첫 배포에서 빠질 수 있어 배포 기준도 다시 정해야 함 | 미채택; 별도 사용자 합의 필요 |

이 범위 표는 기능·조건의 수와 순서를 정리한 것이며 3명·10일 내 완료 가능성을 추정한 일정표가 아니다. 소요 시간·담당자·의존성은 이슈 단계에서 검토한다. 범위 승인 후 API 계약 단계로 진행했다(ADR-024).
