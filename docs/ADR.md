# 결정 기록 (ADR)

제품 동작·데이터 구조·API 계약을 선택한 배경과 비용을 기록한다. 각 ADR의 날짜는 결정 시점(Asia/Seoul)이며, 과거 결정을 최신 규칙으로 덮어쓰지 않고 후속 ADR에서 대체 관계를 표시한다. 현재 구현 기준은 아래 표와 연결 명세를 따른다.

## 기록 읽는 기준

- ‘대체’ 또는 ‘부분 대체’ 상태의 본문은 당시 검토한 설계다. 과거 토큰·지급·API 별칭을 현재 계약으로 사용하지 않는다.
- 문서 검토·설정 파일 작성과 애플리케이션 구현·DB 적용·배포 검증을 구분한다.
- 이유는 설계의 목적·장단점·감수하는 비용을 설명한다. 확정되지 않은 제품 정책이나 검증 결과를 추가하지 않는다.
- 기존 ‘다시 볼 때’는 유지하고 미정인 시점은 비워둔다. 연결 문서는 [README](../README.md), [API](API.md), [DB](DB.md), [이슈 목록](issues.md)이다.

## ADR-001 — 프로젝트 기술과 작업 조건

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 부트캠프 수강생 3명이 10일 동안 진행하는 팀 프로젝트다.
- 결정: React(JavaScript)·React Router·axios / Express 5·Prisma 7·PostgreSQL을 사용하고 Netlify·Render·Neon에 배포한다. 비밀번호는 bcrypt로 해시해 저장한다. 로그인·파일 업로드·TypeScript·명시하지 않은 라이브러리는 사용하지 않는다. 설계 확정과 애플리케이션 구현은 별도 단계로 진행한다.
- 이유: 3명·10일 일정에서는 기술 조합을 고정해 환경 설정과 학습 비용을 줄여야 한다. 클라이언트와 서버 모두 JavaScript를 사용하고, 관계형 데이터와 배포 구성을 공통 기준으로 맞춰 기능 구현에 집중한다.
- 영향: 문서와 후속 구현 계획은 이 조건 안에서 작성한다.
- 후속 변경: 추가 라이브러리의 합의된 절차와 emoji-picker-react 사용 예정은 ADR-017에서 관리한다.
- 다시 볼 때: 범위와 이슈 목록 작성 시.

## ADR-002 — 첫 배포 기준일과 완료 범위

- 날짜: 2026-10-08
- 상태: 일정·인수 범위는 ADR-055로 대체; 당시 ‘첫 주 월요일’ 지정을 대체한 기록
- 배경: 첫 배포는 10/16 전체 사용자 흐름 검증을 기준으로 삼는다. 이후 축소 구현 목표는 10/14로 앞당겼다.
- 결정: 첫 주 금요일인 2026-10-16까지 배포 주소에서 전반적인 모든 사용자 흐름이 처음부터 끝까지 동작해야 한다.
- 이유: 배포 주소에서 전체 흐름을 검증해야 로컬 환경에서 드러나지 않는 라우팅·CORS·DB 연결 문제를 확인할 수 있다. 첫 주에 통합 결과를 확보해 남은 기간을 결함 수정과 화면 완성에 사용할 수 있도록 한다.
- 영향: 첫 배포 검증은 전체 사용자 흐름을 대상으로 한다.
- 다시 볼 때: 범위와 이슈 목록 작성 시 배포 검증 항목 확인.

## ADR-003 — 비밀번호 확인 효력의 만료 기준

- 날짜: 2026-10-08
- 상태: ADR-038로 대체 — 자정까지의 검증 효력 정책 폐기
- 배경: 로그인 없이 스터디 비밀번호로 보호 기능에 접근하며 확인 효력의 유효기간이 필요하다.
- 결정: 비밀번호 확인 효력은 다음 한국 시각 자정에 만료된다. 만료 후 보호 기능을 이용하려면 다시 확인해야 한다.
- 이유: 하루를 기준으로 확인 효력을 제한하면 날짜 경계를 명확하게 설명할 수 있다. 다만 자정 직전 확인의 유효시간이 짧아지고 실행 중인 기능과 만료가 충돌할 수 있어 후속 인증 설계가 필요했다.
- 영향: 자정 직전에 확인해도 자정에 만료된다. 효력을 공유할 화면·작업 범위와 자정을 넘겨 실행 중인 기능의 처리는 아직 정하지 않았다.
- 관련 기능: F-AU-001, F-AU-002
- 다시 볼 때: 화면과 API 계약 작성 시 재확인 흐름 및 효력 공유 범위 검토.
- 후속 보완: 당시 미정이던 확인 효력 공유 범위는 ADR-018에서 습관·집중끼리 공유, 수정·삭제 매번 확인으로 확정했다.

## ADR-004 — 오늘의 습관 날짜 경계

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 원문은 체크 여부가 매일 초기화되고 날짜별 기록은 조회돼야 한다고 정한다.
- 결정: 오늘의 습관 체크는 매일 한국 시각 자정을 기준으로 새 날짜의 상태를 초기화한다. 이전 날짜의 기록은 보존한다.
- 이유: 서버와 브라우저의 시간대가 달라도 같은 행동을 같은 날짜에 기록해야 한다. 한국 날짜를 공통 기준으로 사용하면 자정 초기화·오늘 체크·주간 기록 조회의 기준이 일치하며, 초기화를 위해 과거 데이터를 삭제할 필요가 없다.
- 영향: 체크·해제와 기록 조회는 한국 날짜를 기준으로 일관되게 처리해야 한다.
- 관련 기능: F-HB-005, F-HB-006, F-ST-010
- 다시 볼 때: API 계약과 테이블 작성 시 날짜 경계 검토.

## ADR-005 — 내부 페이지 이동 중 타이머 유지

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 집중 도중 다른 페이지로 이동했을 때의 동작은 원문에 없다.
- 결정: 서비스 내부 페이지 이동 시 타이머는 계속 진행한다.
- 이유: 습관 확인이나 홈 이동만으로 집중이 끊기면 페이지 탐색과 시간 기록이 충돌한다. 타이머 진행을 화면의 생명주기와 분리해 내부 이동 중에도 같은 집중을 이어갈 수 있도록 한다.
- 영향: 집중 화면을 벗어나도 진행 중인 시간 상태를 유지해야 한다.
- 관련 기능: F-FC-006
- 다시 볼 때: 화면과 API 계약 작성 시 상태 유지 흐름 검토.

## ADR-006 — 새로고침 후 서버 기준 시간 복원

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 새로고침으로 화면 상태가 사라졌을 때의 시간 복원 기준이 필요하다.
- 결정: 새로고침하면 서버 데이터로 타이머의 남은 시간을 재계산한다.
- 이유: 브라우저의 카운트다운 값만 저장하면 새로고침·백그라운드 지연·기기 시각 변경에 따라 남은 시간이 달라질 수 있다. 서버에 저장된 시간 정보로 다시 계산해 표시 시간과 완료 판정의 기준을 맞춘다.
- 영향: 시간 복원에 필요한 상태를 서버에서 확인할 수 있어야 한다. 저장 필드는 테이블 단계에서 정한다.
- 관련 기능: F-FC-007
- 다시 볼 때: API 계약과 테이블 작성 시 저장할 타이머 상태 검토.

## ADR-007 — 외부 이탈 시 일시정지와 복귀 상태

- 날짜: 2026-10-08
- 상태: ADR-052로 대체 — 외부 이탈 자동 일시정지 제외
- 배경: 외부 주소 이동·창 닫기와 서비스 내부 페이지 이동을 구분해야 한다.
- 결정: 외부 주소 이동 또는 창 닫기 시 타이머를 일시정지하고, 복귀하면 떠난 시점의 남은 시간을 유지한 일시정지 상태를 보여준다.
- 이유: 당시에는 서비스를 완전히 떠난 시간을 집중으로 인정하지 않으면서 진행 중 기록을 보존하는 것이 목표였다. 삭제 대신 일시정지로 남겨 복귀 후 재개할 수 있게 했으나 종료 감지의 신뢰성과 구현 비용 때문에 ADR-052에서 대체했다.
- 영향: 내부 이동·새로고침·외부 이탈의 처리 흐름을 구분해야 한다. 브라우저 이탈 감지와 일시정지 시점 확정 방식, 복귀 후 재개 조작은 아직 정하지 않았다.
- 관련 기능: F-FC-008, F-FC-009
- 다시 볼 때: 화면 및 API 계약 작성 시 재개 흐름, 브라우저 이탈 감지의 제약과 시간 확정 방식 검토.
- 후속 보완: 복귀 후 재개 조작은 ADR-020에 따라 Start로 남은 시간부터 진행한다.

## ADR-008 — 요구사항 추적과 결정 기록 분리

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 원문 요구사항과 기능 목록·API·이슈의 연결을 추적할 공통 식별 체계가 필요하다.
- 결정: README.md에 원문 참조번호·기능 ID·요구사항 반영 체크를 두고 기존 결정 기록은 ADR.md로 이전한다. 원문에 번호가 없으므로 제목 순서 기반 참조번호임을 명시하며 brief.md는 수정하지 않는다.
- 이유: 기능 ID와 원문 참조를 연결하면 요구사항 누락을 확인하고 화면·API·이슈의 연결을 추적할 수 있다. 현재 명세와 결정 이력을 분리해 기능 설명은 간결하게 유지하면서 변경 이유는 ADR에서 확인한다.
- 영향: ‘명세 반영’과 ‘구현 완료’를 구분한다. 앞으로 확인된 결정은 ADR에 기록한다. 문서 하나씩 작성하고 단계별 검토 후 다음 명세로 진행하는 방식은 유지한다.
- 다시 볼 때: 화면·API·이슈 작성 및 요구사항 변경 시 참조 관계 확인.

## ADR-009 — 피그마 화면 이름과 화면 주소

- 날짜: 2026-10-08
- 상태: 주소 및 생성·수정 목적 확정; 화면 세부 동작 확인 중
- 배경: 피그마 화면 6개와 React Router 주소를 일치시켜야 한다.
- 결정: 아래 주소를 사용한다. 피그마 화면 이름을 유지하고 실제 서비스 목적은 README의 별도 열에 명시한다.

| 화면 이름 — 피그마 기준 | 주소 | 서비스 목적 |
| --- | --- | --- |
| 홈 | `/` | 스터디 탐색 |
| 상세 페이지 | `/reg` | 스터디 생성 |
| 상세 페이지_수정 | `/reg?id={id}` | 스터디 정보 수정 |
| 스터디 상세 | `/dashboard/{id}` | 해당 스터디 상세 |
| 오늘의 습관 | `/routines?id={id}` | 해당 스터디의 오늘의 습관 |
| 오늘의 집중 | `/challenge?id={id}` | 해당 스터디의 오늘의 집중 |

- 이유: 디자인 화면명과 URL을 공통으로 사용하면 프론트 라우팅과 화면 검증에서 같은 대상을 가리킬 수 있다. 생성·수정 화면은 ID 유무로 구분하되, 화면 주소와 서버 API 경로는 서로 다른 역할로 관리한다.
- 영향: 생성·수정은 `/reg`에서 ID 쿼리 유무로 구분한다. 상세는 경로에, 습관·집중은 쿼리에 스터디 ID를 포함한다. 앞서 제안한 `/studies/...` 주소는 채택하지 않는다. 비밀번호 확인 UI·효력 공유 범위는 이 결정에 포함하지 않는다.
- 관련 화면: S-001~006
- 다시 볼 때: 화면·주소 표 승인 전 및 API 계약 작성 시 ID 전달·직접 접근·잘못된 ID 처리 확인.

## ADR-010 — 홈 이동과 작업 결과 처리

- 날짜: 2026-10-08
- 상태: 확정; 모달 나가기 적용 범위 확인 대기
- 배경: 화면 이동과 성공·실패 피드백의 공통 기준이 필요하다.
- 결정: 로고와 습관·집중의 홈 버튼은 /로 이동한다. 생성·수정 성공 시 해당 /dashboard/{id}로 이동한다. 삭제 성공 시 /로 이동한 뒤 에러토스트 형식의 삭제 성공 알림을 표시한다. 각 기능에는 별도 취소가 없고 실패 시 해당 페이지를 유지한다.
- 이유: 성공 후 이동 지점을 고정하면 생성·수정 결과 확인과 삭제 후 복귀가 예측 가능해진다. 실패 시 입력과 현재 화면을 유지해 재시도할 수 있게 하고, 모달 닫기와 실제 요청 중단은 별도로 취급한다.
- 영향: BR-08의 스터디 홈 목적지를 /로 확정한다. 성공 알림의 정확한 문구는 미정이다. 비밀번호 모달의 나가기는 시안에 남아 있으므로 취소 없음의 적용 범위를 추가 확인한다.
- 관련 기능·화면: F-HB-003, S-001~006
- 다시 볼 때: 화면 명세 보완 시 모달 나가기의 범위 확인; 오류 표현은 해당 기능 구현 시.
- 후속 보완: 당시 미정이던 취소와 모달 나가기의 범위는 ADR-019로 확정했다. 취소 없음은 요청 중단 기능 없음이며 모달 닫기는 허용한다.

## ADR-011 — 자체 디자인 비밀번호 모달

- 날짜: 2026-10-08
- 상태: 자체 모달 UI 유지; 현재 페이지별 검증은 ADR-051
- 배경: 수정 진입을 포함한 보호 화면에 공통 비밀번호 입력 UI가 필요하다.
- 결정: 보호 기능의 비밀번호 입력은 자체 디자인 모달을 사용한다. 제목·권한 안내·입력·비밀번호 표시 전환·진입 버튼·나가기를 공통 구성으로 둔다.
- 이유: 보호 기능마다 입력 UI가 달라지는 것을 막고 비밀번호 표시·오류 안내·닫기 동작을 공통으로 제공한다. 모달의 모양을 재사용하더라도 서버 검증 범위와 확인 효력은 별도 정책으로 관리한다.
- 영향: 기존 자정 만료는 유지한다. 모달 채택만으로 보호 기능 사이의 확인 효력 공유를 결정하지 않는다. 직접 접근 시 배경 화면과 모달 나가기 적용 범위도 미정이다.
- 관련 기능·화면: F-AU-001~002, S-003~006
- 다시 볼 때: 화면 명세 보완 및 API 계약 작성 시 공유 범위·직접 접근·만료 동작 검토.
- 후속 보완: 당시 미정이던 확인 효력 공유 범위와 모달 닫기는 ADR-018~019에서 확정했다.

## ADR-012 — 더보기와 진행 일수 기준

- 날짜: 2026-10-08
- 상태: 일부 확정
- 배경: 홈 목록의 추가 조회와 진행 일수 계산 기준을 정리한다.
- 결정: 더보기는 offset 방식으로 6개를 추가 조회하고 기존 항목을 유지한다. 카드의 진행 일수는 스터디 생성일 기준으로 센다.
- 이유: 기존 목록을 유지한 채 6개씩 추가하면 탐색 위치를 잃지 않고 다음 항목을 볼 수 있다. offset은 초급 팀이 구현·확인하기 쉬운 방식이며, 진행 일수는 생성일이라는 공통 데이터로 계산한다.
- 영향: 최초 조회 개수·최근 조회 개수·검색 대상·기본 정렬은 미정이다. 생성 당일을 0일로 볼지 1일로 볼지도 아직 정하지 않았다.
- 관련 기능·화면: F-ST-002, F-ST-014, S-001
- 다시 볼 때: 화면 명세 보완 및 API 계약 작성 시 초기·추가 조회와 날짜 계산 검토.

## ADR-013 — 타이머 시간 변경 진입

- 날짜: 2026-10-08
- 상태: 진입 조작 확정; 나머지 상태 동작 미정
- 배경: 집중 시간 설정 진입점과 타이머 상태별 버튼 동작을 구분해야 한다.
- 결정: 초기 화면의 타이머 숫자를 클릭하면 집중 시간을 변경할 수 있다. 실행 캡처의 버튼·색상은 관찰 기록으로 반영한다.
- 이유: 초기 화면의 큰 시간 숫자를 설정 진입점으로 사용해 시안의 조작 흐름을 유지한다. 시간 설정은 시작 전 입력으로 구분하고 진행·일시정지 중 조작과 혼동하지 않도록 상태별 규칙을 별도로 정리한다.
- 영향: 기본 시간·입력 단위·범위, 일시정지·회전 화살표·Start!의 상태별 의미, 빨간색 전환 시점·완료·복귀 조작은 자동으로 확정하지 않는다. 특히 초기화 시 포인트나 진행 기록 처리는 미정이다.
- 관련 기능·화면: F-FC-002~009, S-006
- 다시 볼 때: 추가 시안·세부 동작 검토 및 API 계약 작성 시 타이머 상태 전이 검토.
- 후속 보완: 당시 미정이던 일시정지·초기화·Start의 주요 규칙은 ADR-020, 초기화 직후 정지는 ADR-021, 일시정지에서만 초기화 가능한 조건은 ADR-022에서 확정했다. 기본·최소 10분·최대 180분과 완료 포인트 계산은 ADR-027~028로 확정했다.

## ADR-014 — 상세 제목·응원 상위 3개·링크 복사

- 날짜: 2026-10-08
- 상태: 해당 규칙 확정; 주간 조회·응원 세부 규칙 미정
- 배경: 상세 제목 구성·반응 요약·공유 버튼의 역할을 명확히 해야 한다.
- 결정: 제목에 닉네임과 스터디 이름을 함께 표시한다. 예시의 ‘연우’는 닉네임, ‘개발공장’은 스터디 이름이다. 응원은 반응 수가 가장 많은 이모지 3개와 개수만 노출하고 공유 버튼은 현재 상세 링크를 복사한다.
- 이유: 닉네임과 스터디 이름을 함께 보여 목록과 상세에서 같은 스터디를 식별하게 한다. 상위 3개 반응으로 화면 밀도를 제한하고, 공유는 링크 복사로 제공해 외부 서비스 연동 없이 상세 주소를 전달한다.
- 영향: 공유는 F-ST-013으로 추가한다. 제목 예시를 고정 데이터로 사용하지 않는다. 주간 기록 조회 방식·색상과 응원 선택 UI·중복·동률 규칙은 미정이다.
- 관련 기능·화면: F-ST-007, F-ST-010~013, S-004
- 다시 볼 때: 추가 시안 수신 및 API 계약 작성 시 주간 조회·응원 집계 검토.

## ADR-015 — 폼 입력 제한과 수정 가능 필드

- 날짜: 2026-10-08
- 상태: 확정; 세부 글자 수 계산 기준 미정
- 배경: 생성 폼과 수정 폼에 동일한 입력 제한을 적용해야 한다.
- 결정: 닉네임 필수·최대 10자, 스터디 이름 필수·최대 15자, 소개 필수·최대 100자. 배경은 선택이며 기본값은 첫 초록색. 비밀번호 필수·4~20자이며 전달한 정규식 /^[A-Za-z0-9!@#$%^&*]+$/를 따른다. 비밀번호 확인은 필수이며 동일성을 검증한다. 수정은 닉네임·이름·소개·배경에 한하고 비밀번호는 변경하지 않는다.
- 이유: 입력 길이와 허용 문자를 프론트·서버·DB에서 일치시켜 저장 실패와 화면 넘침을 줄인다. 비밀번호 변경을 제외하면 별도의 변경 검증·복구 절차 없이 스터디 정보 편집에 범위를 한정할 수 있다.
- 영향: 생성 입력과 수정 필드를 구분한다. 비밀번호 접근 모달은 비밀번호 변경과 별개다. 문자열 길이·공백 처리는 API 계약에서 확인하며 이미지에 없는 조합 필수 조건은 추가하지 않는다.
- 관련 기능·화면: F-ST-006, F-ST-008, S-002~003
- 다시 볼 때: API 계약 작성 시 입력 검증·공백·글자 수 계산 기준 검토.

## ADR-016 — 지원 기기와 미정 화면 상태의 결정 시점

- 날짜: 2026-10-08
- 상태: 지원 기기 확정; 나머지 동작 유보
- 배경: 지원 기기와 빈 습관 목록 시안을 기준으로 공통 화면 범위를 정리한다.
- 결정: PC·태블릿·모바일을 지원한다. 빈 습관 목록은 제공 시안의 안내와 목록 수정 진입을 반영한다. 다른 빈 목록은 추가 시안 대기다. 나머지 로딩·오류 등 동작은 해당 부분 구현 시 결정한다.
- 이유: 학습 장소에 따라 PC·태블릿·모바일로 접근할 수 있으므로 핵심 흐름은 세 화면 크기에서 사용할 수 있어야 한다. 확정되지 않은 세부 시안은 구현 단계에서 확인해 문서에 임의의 화면 정책을 추가하지 않는다.
- 영향: 기기별 상세 배치·전환 너비와 미정 상태의 문구·재시도 동작을 현재 임의로 채우지 않는다. 요청 실패 시 해당 페이지 유지라는 ADR-010의 결정은 유지한다.
- 관련 기능·화면: S-001~006
- 다시 볼 때: 추가 빈 목록 시안 수신 및 해당 화면 구현 시.

## ADR-017 — 추가 라이브러리의 합의된

- 날짜: 2026-10-08
- 상태: 추가 선정 원칙 확정; emoji-picker-react 사용 예정
- 배경: 이모지 선택 UI에 사용할 패키지와 추가 의존성의 관리 기준이 필요하다.
- 결정: 이모지 선택 UI에는 emoji-picker-react 도입을 검토한다. 그 외 라이브러리와 개발 의존성은 팀 합의 없이 추가하지 않는다.
- 이유: 짧은 일정에서 의존성이 늘어나면 설치 환경·버전·사용법을 팀 전체가 함께 관리해야 한다. 추가 패키지를 팀 합의로 제한하고, 이모지 선택 UI처럼 필요한 기능에만 도입을 검토한다.
- 영향: ADR-001의 초기 라이브러리 조건에 팀 의존성 검토 절차를 반영한다. 현재 문서만 작성하며 패키지 설치·코드 변경은 수행하지 않는다. 버전과 최종 사용 여부는 아직 정하지 않았다.
- 관련 기능·화면: F-ST-012, S-004
- 다시 볼 때: 이모지 선택 UI 확인 및 의존성 추가·버전을 검토할 때.

## ADR-018 — 비밀번호 확인 효력의 공유 범위

- 날짜: 2026-10-08
- 상태: 인증 공유·자정 만료는 ADR-051로 대체; 삭제 모달 재확인 유지
- 배경: 습관·집중끼리 공유하고 수정·삭제는 매번 확인하는 두 번째 안을 선택했다.
- 결정: 같은 스터디의 오늘의 습관·오늘의 집중에만 확인 효력을 공유하며 다음 한국 시각 자정에 만료한다. 스터디 수정·삭제는 매번 비밀번호를 다시 확인한다.
- 이유: 당시에는 습관과 집중을 오갈 때 반복 입력을 줄이되 정보 변경·삭제 전에는 다시 확인하는 절충안을 택했다. 이후 인증 구조를 단순화하면서 공유 효력은 제거하고 삭제 모달 재확인만 유지한다.
- 영향: 모달 UI 결정 ADR-011과 효력 범위를 구분한다. 다른 스터디로 효력을 공유하지 않는다. 공유 효력의 탭·브라우저 범위와 자정을 넘긴 작업은 미정이다.
- 관련 기능·화면: F-AU-001~002, F-ST-008~009, S-003~006
- 다시 볼 때: API 계약 작성 시 공유 효력 저장·검증과 작업별 재확인 흐름.

### ADR-018 선택지 비교

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 같은 스터디의 보호 기능 전체에 확인 효력 공유 | 반복 입력이 적음 | 수정·삭제도 재입력 없이 가능 | 채택하지 않음 |
| 습관·집중만 공유하고 수정·삭제는 매번 확인 | 변경·삭제 전에 다시 확인 | 수정·삭제 시 입력이 추가됨 | 채택 |

## ADR-019 — 요청 중단과 모달 닫기의 구분

- 날짜: 2026-10-08
- 상태: 명시한 규칙 확정; 영향에 적은 세부 동작 미정
- 배경: 요청 취소와 모달 닫기는 서버 결과에 미치는 영향이 다르다.
- 결정: 진행 중인 요청을 중간에 취소시키는 기능은 없다. 모달의 나가기/취소 버튼은 유지하며, 누르면 모달만 닫고 해당 화면 주소를 유지한다.
- 이유: 모달을 닫는 행동이 이미 서버에 도착한 요청을 취소했다는 뜻은 아니다. 화면 닫기와 요청 중단을 분리해 저장 결과를 잘못 안내하지 않도록 하고, 별도 취소 API와 롤백 흐름은 추가하지 않는다.
- 영향: ADR-010에서 미정이었던 취소 없음의 적용 범위를 확정한다. 요청 중 버튼 활성·비활성이나 모달을 닫은 뒤 도착하는 응답의 처리는 별도 검토 대상으로 남긴다.
- 관련 기능·화면: F-AU-001, S-003~006
- 다시 볼 때: 해당 모달 구현 시 요청 중 조작 및 응답 처리.

## ADR-020 — 타이머 일시정지·초기화·재개 버튼

- 날짜: 2026-10-08
- 상태: 명시한 규칙 확정; 영향에 적은 세부 동작 미정
- 배경: Start·일시정지·초기화 버튼의 상태별 동작을 고정해야 한다.
- 결정: 일시정지는 진행 중에만 동작하고 일시정지 상태에서는 비활성화한다. 회전 화살표는 남은 시간을 초기에 설정했던 시간으로 돌리는 초기화 버튼이다. Start는 진행 중 비활성화하며, 일시정지 상태에서 누르면 멈춘 시간부터 타이머를 재작동한다.
- 이유: 진행 중 Start를 다시 누르거나 정지 상태에서 정지를 반복하는 불필요한 조작을 줄인다. 버튼 상태를 타이머 상태와 연결해 재개·초기화의 의미를 화면과 서버에서 동일하게 처리한다.
- 영향: 일시정지·재개·초기화에 F-FC-010~012를 부여한다. 외부 이탈 후 복귀한 일시정지 상태에서도 Start로 재개한다. 초기화 버튼 활성 조건·초기화 직후 실행 상태·기록 및 포인트 처리·완료 상태 동작은 미정이다.
- 관련 기능·화면: F-FC-003, F-FC-008~012, S-006
- 다시 볼 때: 화면 명세 보완 및 API 계약 작성 시 초기화와 완료 상태 전이.
- 후속 보완: 당시 미정이던 초기화 직후 실행 상태는 ADR-021에서 정지, 초기화 버튼 활성 조건은 ADR-022에서 일시정지로 확정했다. 완료 포인트 계산은 ADR-028로 확정했다. 초기화 후 상태 구분·세션 기록과 완료 후 조작은 별도 확인한다.

## ADR-021 — 타이머 초기화 후 정지

- 날짜: 2026-10-08
- 상태: 초기화 직후 동작 확정; 초기화 버튼 활성 조건 미정
- 배경: 초기화 직후 자동 실행 여부를 구분해야 한다.
- 결정: 회전 화살표로 초기화하면 남은 시간을 초기에 설정했던 시간으로 되돌리고 정지한다. 자동으로 재시작하지 않으며 Start를 눌러 다시 시작한다.
- 이유: 초기화는 새로운 집중 준비와 구분되는 명시적 조작이다. 설정 시간으로 돌아간 뒤 멈추면 이용자가 다음 시작 시점을 선택할 수 있고, 초기화 직후 의도치 않게 시간이 줄어드는 상황을 피할 수 있다.
- 영향: 초기화 후 정지 상태에서 일시정지 버튼은 동작하지 않고 Start로 설정 시간부터 다시 시작한다. 초기화 버튼 활성 조건과 초기화 시 기록·포인트 처리는 아직 정하지 않았다.
- 관련 기능·화면: F-FC-012, S-006
- 다시 볼 때: 화면 명세 보완 및 API 계약 작성 시 초기화 활성 조건·기록·포인트 처리 확인.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 설정 시간으로 돌아간 뒤 정지 | 다시 시작할 시점을 직접 선택 | Start를 눌러야 함 | 채택 |
| 진행 중이었다면 즉시 다시 진행 | 공부 흐름을 이어감 | 누르는 순간부터 시간이 줄어듦 | 채택하지 않음 |

- 후속 보완: 초기화 버튼 활성 조건은 ADR-022에서 일시정지 상태로 한정했다. 기록·포인트 처리와 초기화 후 상태 구분은 별도 확인한다.

## ADR-022 — 초기화 버튼의 활성 상태

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 초기화가 가능한 상태를 클라이언트와 서버에서 동일하게 검사해야 한다.
- 결정: 초기화 버튼은 일시정지 상태에서만 활성화하고 시작 전·진행 중·완료 상태에서는 비활성화한다. 초기화 후 설정 시간으로 돌아가 멈추는 ADR-021의 동작은 유지한다.
- 이유: 진행 중 초기화로 시간과 기록이 바로 바뀌는 실수를 줄이기 위해 먼저 정지를 거치게 한다. 서버도 PAUSED 조건을 검사해 비활성 버튼을 우회한 요청이 진행 상태를 초기화하지 못하도록 한다.
- 영향: 타이머 상태별 버튼 표와 F-FC-012를 갱신한다. 초기화 후 정지를 시작 전·일시정지 중 어느 상태로 분류할지와 기록·포인트 처리는 아직 정하지 않았다.
- 관련 기능·화면: F-FC-012, S-006
- 다시 볼 때: API 계약 작성 시 타이머 상태와 초기화 처리 확인.

## ADR-023 — 범위 문서로 진행 및 우선순위 작성 기준

- 날짜: 2026-10-08
- 상태: 다음 단계 진행과 분류 문서 작성 요청 확정; 기능별 우선순위 제안 검토 대기
- 배경: 필수 범위와 구현 순서를 함께 정리할 기준이 필요하다.
- 결정: 화면·주소 기준으로 MoSCoW 범위와 P0/P1/P2 우선순위를 구분한다. MoSCoW는 포함 필요 정도, P 등급은 구현·통합 순서를 나타낸다. 미정 화면 정책은 해당 기능에서 확인한다.
- 이유: 포함 여부와 구현 순서는 서로 다른 판단이다. MoSCoW로 범위를 정리하고 P0/P1/P2로 연결 순서를 구분해 우선순위가 낮다는 이유만으로 필수 기능이 누락되는 일을 막는다.
- 영향: 기존 36개 기능을 임의로 제외하지 않고 현행 배포 조건 아래 Must로 분류했다. P0 27개·P1 6개·P2 3개는 검토 초안이다. Should·Could로 범위를 낮추거나 배포 기준을 바꾸려면 범위 재합의한다.
- 관련 문서: README.md의 범위와 우선순위 절
- 다시 볼 때: 범위 문서 검토 및 이슈 목록 작성 시 기능별 순서·소요 시간·배포 기준 검토.

## ADR-024 — 범위 승인과 별도 API 문서

- 날짜: 2026-10-08
- 상태: 확정; API 계약의 세부 내용은 작성·검토 중
- 배경: 화면과 범위가 정리된 뒤 API 계약과 수동 검증 예시를 독립적으로 관리한다.
- 결정: README의 MoSCoW·P0/P1/P2를 범위 기준으로 사용한다. API 계약은 docs/API.md, 수동 요청 예시는 api/api.http에서 관리하고 README에서 연결한다.
- 이유: API 계약과 수동 요청 예시를 나란히 관리하면 프론트·백엔드가 요청 필드와 기대 응답을 함께 확인할 수 있다. README에는 전체 흐름을 남기고 세부 계약은 별도 문서로 분리해 수정 지점을 명확하게 한다.

- 관련 문서: README.md, API.md, api.http
- 다시 볼 때: API Docs와 요청 예시 검토 및 다음 단계 승인 시.

## ADR-025 — 임시 확인 토큰의 헤더 전달

- 날짜: 2026-10-08
- 상태: ADR-038로 대체 — 임시 토큰 전달 대신 보호 요청마다 비밀번호 검증
- 배경: 습관·집중 비밀번호 확인의 효력을 후속 API 요청에 전달해야 한다.
- 결정: 서버가 발급한 임시 확인 토큰을 요청 헤더로 전달한다. 서버가 다음 한국 시각 자정 만료를 검사한다. 같은 스터디의 습관·집중 공유, 수정·삭제 매번 재확인은 유지한다.
- 이유: 당시 헤더 토큰은 쿠키 자동 전송에 의존하지 않고 요청별 확인값을 명시할 수 있는 선택이었다. 대신 보관·서명·만료 정책이 필요해 이후 규모 축소 과정에서 요청별 비밀번호 검증으로 대체한다.
- 영향: API.md는 Authorization: Bearer와 verificationToken·expiresAt 응답을 제안한다. 토큰의 스터디·용도·만료를 서버에서 검사한다. 프론트 보관 위치·탭 범위와 수정·삭제용 토큰 소비·재시도는 아직 확정하지 않는다.
- 관련 기능: F-AU-001~002, 모든 보호 API
- 다시 볼 때: API 계약 검토 및 프론트 요청 공통 처리·자정 만료 구현 시.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 서버 발급 임시 토큰을 요청 헤더에 전달 | 요청에서 전달값이 명시적이며 브라우저의 쿠키 자동 전송에 의존하지 않음 | 프론트가 보호 요청마다 헤더를 붙여야 함 | 채택 |
| 쿠키로 전달 | 브라우저가 자동 전송 | 분리 배포 환경의 쿠키·교차 출처 설정이 필요 | 채택하지 않음 |

## ADR-026 — 스터디당 활성 타이머 1개

- 날짜: 2026-10-08
- 상태: 스터디당 RUNNING/PAUSED 합계 1개 유지; 브라우저 소유권은 ADR-052로 제외
- 배경: 같은 스터디에 여러 브라우저가 접근할 때 타이머의 기준이 필요하다.
- 결정: 스터디당 활성 타이머는 1개로 제한한다. 브라우저마다 별도의 활성 세션을 만들지 않는다.
- 이유: 스터디당 하나의 진행 기준을 두면 조회·일시정지·완료·포인트의 대상이 명확하다. 활성 상태를 DB에서 제한해 별도 브라우저 세션 테이블 없이도 새 집중이 겹쳐 생성되는 것을 막는다.
- 영향: 동시 시작으로 활성 세션이 두 개 생기지 않도록 서버가 검사해야 한다. API.md는 충돌 시 409 FOCUS_CONFLICT와 현재 상태 재조회를 제안한다. 일시정지의 활성 포함 여부·여러 브라우저의 조작 권한·외부 이탈 충돌은 별도로 확인한다.
- 관련 기능: F-FC-001~012
- 다시 볼 때: API 계약 검토 및 타이머 동시 요청 구현 시.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 스터디당 활성 타이머 1개 | 상태·완료·지급 기준을 하나로 관리 | 여러 사람이 독립된 타이머로 동시에 집중할 수 없음 | 채택 |
| 브라우저별 활성 타이머 | 각각 독립된 시간으로 집중 가능 | 브라우저 구분·여러 세션·포인트 처리 규칙이 추가로 필요 | 채택하지 않음 |

## ADR-027 — 집중 시간 입력과 최대 포인트

- 날짜: 2026-10-08
- 상태: 시간 입력 확정; 지급 규칙은 ADR-029로 변경, 기존 최대 20P는 ADR-031로 해제
- 배경: 기본 시간과 입력 범위가 원문·캡처만으로 정해지지 않았다.
- 결정: 집중 시간은 기본·최소 10분, 최대 180분이며 분 단위로 설정한다. 집중 완료 1회에서 얻는 최대 포인트는 20P다.
- 이유: 기본값과 입력 단위를 고정해 화면 설정과 서버 검증을 단순하게 한다. 10~180분 범위를 공통으로 적용하되 포인트 상한은 지급 공식과 별개이며 후속 정책에서 일관되게 조정한다.
- 영향: 캡처의 25:00을 기본값으로 사용하지 않는다. API.md는 durationMinutes 정수 10~180을 필수 입력으로 제안한다. 범위를 벗어나거나 분 단위가 아닌 값은 거절한다.
- 관련 기능: F-FC-002~005, S-006
- 다시 볼 때: API 시간 검증·시간 설정 UI 구현 시.

## ADR-028 — 첫 10분과 완료 포인트 계산

- 날짜: 2026-10-08
- 상태: ADR-029로 대체됨; 이전 결정과 당시 이유를 보존
- 배경: 당시 시간별 지급 예시는 10분 3P, 20분 4P, 25분 4P, 180분 20P였다. 후속 포인트 개편으로 대체된 계산식이다.
- 결정: 설정한 집중을 완료했을 때 첫 10분에 3P를 지급하고, 이후 완성한 10분마다 1P를 더한다. 계산식은 3 + floor((설정 분 - 10) / 10)이다. 10분 미만 나머지는 점수 증가에 포함하지 않는다. 10~180분 범위의 지급량은 3~20P다.
- 이유: 당시 공식은 첫 10분의 기본 보상을 중복 계산하지 않으면서 시간별 예시를 일치시키기 위한 것이었다. 이후 경과 보상과 목표 보상을 분리하는 정책으로 바뀌었으므로 현재 지급 공식으로 사용하지 않는다.
- 영향: 포인트는 완료 시 지급한다. 첫 10분에 별도 1P를 추가하지 않으며, 이전 질문의 min(20, 3 + floor(분 / 10)) 제안은 채택하지 않는다. 일시정지·초기화·조기 완료 요청만으로 포인트를 지급하지 않는다. 완료 재요청의 HTTP 응답과 세션 처리 방식은 API에서 별도 검토한다.
- 관련 기능: F-FC-004~005, BR-14, API-FC-06
- 다시 볼 때: 완료·중복 지급 방지 구현 및 10·20·25·180분 경계 검증 시.

## ADR-029 — 경과 시간 보상과 목표 달성 보상 분리

- 날짜: 2026-10-08
- 상태: ADR-053으로 대체 — 부분 경과/초기화 지급 제외, 완료 때만 지급
- 배경: 기존 완료 보상을 경과 시간 보상과 목표 달성 추가 보상으로 분리하는 정책을 검토했다.
- 결정: 집중 목표 시간 달성 여부와 관계없이 10분 경과마다 1P를 지급한다. 이용자가 설정한 집중 목표 시간을 달성하면 추가 3P를 지급한다. 기존 ADR-028의 완료 시 계산식을 대체한다.
- 이유: 당시에는 목표 미달성 집중에도 일정 경과 보상을 주고 목표 완료를 추가 보상으로 구분하려 했다. 지급 시점과 중복 방지 구조가 커져, 현재는 ADR-053의 완료 전용 지급으로 범위를 줄였다.
- 영향: F-FC-005는 '집중 포인트 획득'으로 명칭을 바꾸되 ID·Must·P0는 유지한다. 목표 미달성만을 이유로 경과 보상을 지급 대상에서 제외하지 않는다. 180분 목표 달성 시 새 규칙의 합은 18 + 3 = 21P다. ADR-027의 기존 최대 20P는 후속 결정 ADR-031에서 해제했다. 일시정지·재개·초기화의 경과 합산·이미 받은 포인트 처리·서버 지급 반영 시점은 아직 정하지 않는다.
- 관련 기능: F-FC-002~005, F-FC-010~012, BR-14
- 다시 볼 때: API·DB 설계 재개 시 경과 시간·상태 변경·지급 반영 검토.

## ADR-030 — 포인트 변경의 반영 범위와 API 수정 보류

- 날짜: 2026-10-08
- 상태: 기록 당시 보류; 이번 명세 갱신 범위는 ADR-039로 해제
- 배경: 포인트 정책 개편에 맞춰 API 갱신과 DB 검토의 순서를 조정해야 했다.

## ADR-031 — 기존 20포인트 상한 해제

- 날짜: 2026-10-08
- 상태: 확정; ADR-027 중 최대 포인트 20P 결정을 대체
- 배경: ADR-029의 새 규칙을 180분에 적용하면 경과 보상 18P와 목표 달성 보상 3P로 총 21P가 되어 기존 20P 상한과 충돌한다.

- 다시 볼 때: API·DB 설계 재개 및 180분 목표 달성 검증 시.

| --- | --- | --- | --- |
| 기존 20P 상한 해제 | 새 지급 규칙을 그대로 적용 | 이전 최대 20P 결정 변경 | 채택 |
| 기존 20P 상한 유지 | 기존 상한 유지 | 상한 이후 보상 제한 방식을 추가로 정해야 함 | 채택하지 않음 |

## ADR-032 — DB 초안 우선 검토와 테이블 종류 구상

- 날짜: 2026-10-08
- 상태: DB 설계로 진행 확정; 테이블 구성은 제안 검토 중
- 배경: API 윤곽은 있으나 습관 기록과 포인트의 저장 규칙 검토가 남아 있었다.
- 결정: 기존 API 윤곽을 바탕으로 테이블 종류·역할·기록 보존 구조를 먼저 검토한다. 이후 관계·컬럼·제약을 구체화하고 API 계약과 다시 대조한다.
- 이유: 습관 기록 보존과 집중 지급 이력은 테이블 구조에 직접 영향을 준다. 기존 API 윤곽을 기준으로 PK·FK·상태 저장을 먼저 검토하면 요청·응답을 구체화할 때 저장 불가능한 계약을 줄일 수 있다.
- 영향: README의 진행 순서를 갱신한다. 제안한 테이블 이름·개수·저장 방식은 확정 정책으로 간주하지 않는다. DB 초안 이후 API 계약을 구체화하고 두 문서를 대조한다.
- 관련 문서: README.md, ADR.md, 후속 DB 초안
- 다시 볼 때: 테이블 종류 검토 후 관계·컬럼·제약 조건을 구체화할 때.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| API 계약 완성 후 DB 설계 | 프론트·백엔드가 사용할 계약을 먼저 맞출 수 있음 | 저장 규칙 검토 결과에 따라 계약 재수정 가능 | 이번 진행 순서로 채택하지 않음 |
| 기존 API 윤곽을 바탕으로 DB 초안 먼저 검토 | 기록 보존·포인트 지급 구조를 먼저 확인 | 화면 요구와 대조하고 API를 다시 맞춰야 함 | 채택 |

## ADR-034 — 6개 테이블 DB 설계와 별도 ERD 문서

- 날짜: 2026-10-08
- 상태: 테이블 수·구조는 ADR-052~053의 5개 모델로 대체; 별도 ERD 문서 유지
- 배경: 인증 토큰 테이블을 제외한 서비스 데이터의 관계·선택성·정규화를 함께 검토한다.
- 결정: Study, Routine, RoutineHistory, Challenge, PointHistory, Reaction의 6개 테이블로 DB.md와 api/prisma/schema.prisma 초안을 작성한다. VerificationToken은 이번 설계에서 제외한다.
- 이유: 테이블 이름만으로는 관계차수·선택성·삭제 영향이 드러나지 않는다. ERD·컬럼 사전·스키마를 함께 관리해 기록 보존과 Cascade 삭제를 DB 적용 전에 검토할 수 있게 한다.
- 영향: API.md·api.http의 수정 보류는 유지한다. 토큰 테이블 제외를 서버 검증 생략 승인으로 해석하지 않는다. PK·FK·NULL·복합키·정규화·DB 추가 제약을 문서와 스키마에서 대조한다. DB 적용·마이그레이션·패키지 설치는 수행하지 않는다.
- 관련 문서: DB.md, api/prisma/schema.prisma, README.md
- 다시 볼 때: DB 문서·스키마 검토 및 채택 시.

## ADR-035 — 초기화 시 경과 시간 초기화와 포인트 보존

- 날짜: 2026-10-08
- 상태: 경과 초기화·다음 새 행은 ADR-052 유지; 초기화 보상은 ADR-053으로 제외
- 배경: 최신 포인트 제도에서 초기화 전에 받은 10분 경과 보상의 처리 기준이 필요했다.
- 결정: 타이머 초기화 시 그전 경과 시간을 0으로 돌리고 이미 지급된 포인트는 유지한다. 설정했던 시간으로 복원 후 정지하는 기존 동작은 유지한다.
- 이유: 당시에는 초기화로 이미 받은 보상을 회수하지 않고 다음 시도의 시간만 새로 계산하려 했다. 현재는 완료 전 지급 자체를 제거했으므로 초기화 보상 보존을 위한 별도 원장·시도 번호가 필요하지 않다.
- 영향: DB 초안은 같은 Challenge의 attemptNumber를 증가시키고 이전 시도의 PointHistory를 보존하는 구조를 제안한다. 새로운 시도와 기존 지급 키를 구분한다. 초기화 후 상태를 PAUSED로 표현하는 것은 기술 제안이며 UI 상태 분류를 추가로 확정한 것은 아니다.
- 관련 기능: F-FC-005, F-FC-012
- 다시 볼 때: DB 초안 검토 및 초기화·중복 지급 구현 시.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 경과 0·지급 유지 | 이미 받은 보상과 이력 보존 | 이후 시도를 구분해야 함 | 채택 |
| 경과 0·지급 회수 | 초기화에 따른 보상 취소 가능 | 차감·취소 규칙 필요 | 미채택 |
| 경과 계속 누적 | 전체 경과 유지 | 목표 타이머·보상 기준 분리 필요 | 미채택 |

## ADR-036 — 브라우저별 같은 이모지 응원 1회

- 날짜: 2026-10-08
- 상태: 제한 규칙 확정; 브라우저 식별 방식은 기술 제안
- 배경: 반복 응원 허용 여부에 따라 Reaction을 누적 카운터 또는 개별 응원 행으로 설계해야 한다.
- 결정: 같은 스터디에서 브라우저별 같은 이모지 응원을 1회로 제한한다.
- 이유: 한 브라우저가 같은 이모지를 반복해서 증가시키는 행동을 줄이면서 로그인은 도입하지 않는다. 복합키로 중복을 제한하되 browserId는 변경 가능하므로 개인별 영구 제한으로 설명하지 않는다.
- 영향: Reaction에 studyId·browserId·emoji를 복합 PK로 제안하고 응원 수는 COUNT(*)로 집계한다. browserId의 생성·저장·재발급은 이번 DB 문서의 기술 제안이다. 저장소를 지우거나 식별자를 바꾸면 다시 응원할 수 있는 한계를 명시하며 개인 신원 확인으로 설명하지 않는다.
- 관련 기능: F-ST-011~012
- 다시 볼 때: 브라우저 식별 제안 검토, 응원 API 계약 재개 및 중복 응원 검증 시.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 반복 허용 | 식별 없이 카운터로 처리 | 한 브라우저가 계속 증가 가능 | 미채택 |
| 브라우저별 같은 이모지 1회 | 같은 브라우저의 반복 증가를 줄임 | 브라우저 구분 데이터·재발급 기준 필요 | 채택 |

## ADR-037 — 스터디 전체 삭제 시 연결 데이터 삭제

- 날짜: 2026-10-08
- 상태: 확정
- 배경: 스터디 삭제 뒤 습관·기록·집중·포인트 이력·응원의 보존 여부가 정해지지 않았다.
- 결정: 스터디를 삭제하면 연결된 Routine, RoutineHistory, Challenge, PointHistory, Reaction도 함께 삭제한다.
- 이유: 스터디가 없어졌는데 연결 기록만 남으면 조회 대상과 관리 기준이 불명확해진다. 전체 삭제는 Cascade로 정리하고, 과거 기록을 보존해야 하는 개별 습관 종료는 소프트 삭제로 분리한다.
- 영향: DB 초안의 FK 삭제 동작은 Cascade다. 일반 습관 종료는 Routine.endsOn 변경으로 과거 기록을 보존하는 별도 동작이며, 스터디 전체 삭제와 혼동하지 않는다. 수정·삭제 매번 비밀번호 재확인 규칙은 유지한다.
- 관련 기능: F-ST-009, F-HB-008
- 다시 볼 때: DB 초안 검토 및 스터디 전체 삭제·개별 습관 종료 구현 시.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 연결 데이터 함께 삭제 | 삭제 후 남는 데이터 없이 관리 | 과거 기록도 함께 없어짐 | 채택 |
| 삭제 후 기록 보존 | 과거 데이터 유지 | 삭제 표시·보관·조회 기준 필요 | 미채택 |

## ADR-038 — 페이지 진입마다 API 검증과 보호 요청별 비밀번호 전달

- 날짜: 2026-10-08
- 상태: 현재 정책은 ADR-051; 과거 제안이던 비밀번호 헤더를 채택
- 배경: 보호 페이지마다 비밀번호를 확인하고 후속 요청도 서버에서 검증하는 계약이 필요하다.
- 결정: /routines?id={id}, /challenge?id={id}, /reg?id={id}에 진입할 때마다 해당 페이지에서 스터디 비밀번호를 API로 검증한다. 직접 접속·재진입·새로고침도 다시 확인하며 습관↔집중 검증 효력을 공유하지 않는다. 이후 습관 조회·체크·편집, 집중 조회·조작, 수정 저장 등 모든 보호 요청에도 비밀번호를 전달하고 서버가 매번 bcrypt로 비교한다. 삭제는 스터디 상세에서 삭제 모달을 열어 비밀번호를 받고 삭제 요청 자체에서 검증한다.
- 이유: 페이지 진입 성공 여부만 브라우저가 기억하면 후속 보호 요청을 위조할 수 있다. 매 요청에서 서버가 비밀번호와 소속을 확인해 인증 판단을 서버에 두며, 토큰 발급·저장·만료 구성은 줄인다.
- 영향: ADR-003의 자정 인증 만료, ADR-018의 습관·집중 공유 효력, ADR-025의 임시 토큰 헤더 전달은 대체한다. VerificationToken·검증 세션 테이블은 만들지 않으며 기존 6개 DB 모델·관계는 유지한다. 비밀번호는 현재 페이지 메모리에만 보관하고 페이지 이탈·재진입·새로고침 때 이전 검증을 재사용하지 않는다. 원문·검증 상태를 DB·LocalStorage·쿠키에 저장하지 않는다. Study.passwordHash만 저장하며 응답에 노출하지 않는다.
- API 제안: 페이지 진입은 POST /studies/{studyId}/password-verifications에 password를 보내고 verified 결과만 받는다. 이후 보호 요청은 GET에도 사용할 수 있는 X-Study-Password 헤더로 비밀번호를 전달한다. 서버는 매 요청에서 대상 Study와 하위 데이터 소속·비밀번호를 확인한다. 배포 요청은 HTTPS를 사용하고 CORS에서 해당 헤더를 허용해야 한다. 라이브러리는 추가하지 않는다.
- 유지하는 규칙: 자체 디자인 모달, 모달 나가기/취소 시 주소 유지, 실패 시 현재 페이지 유지, 습관의 한국 시각 자정 날짜 경계, 내부 페이지 이동 중 타이머 진행·새로고침 후 서버 데이터 복원, 스터디 삭제 후 홈 이동·성공 알림.
- 관련 기능·화면: F-AU-001~002, F-ST-008~009, F-HB-001~008, F-FC-001~012, S-003~006
- 다시 볼 때: 인증 계약 검토와 프론트 페이지 전환·서버 보호 API·외부 이탈 요청 구현 시. 매 요청 bcrypt 검증 비용과 비밀번호 메모리 수명을 확인한다.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 보호 요청마다 비밀번호 전달 | 토큰 발급·저장·만료 로직과 토큰 테이블 없이 서버에서 검증 가능 | 페이지 메모리에 원문 보관, 반복 전송·bcrypt 검증 비용 발생 | 채택 |
| 페이지 진입 검증 후 서버 서명 임시 토큰 전달 | 비밀번호 반복 전송·bcrypt 검증 감소, 토큰 테이블 없이도 가능 | 서명·만료 검증 로직과 별도 토큰 수명 결정 필요 | 미채택 |

## ADR-039 — 집중 활성 범위·초기화 상태·정산 시점·나머지 처리 확정

- 날짜: 2026-10-10
- 상태: 활성 1개·RESET 뒤 새 행 유지(ADR-052); 초기화 정산은 ADR-053으로 제외
- 배경: 일시정지 중 새 시작·초기화 후 상태·지급 시점·나머지 시간 처리 기준을 정리했다.
- 결정: 브라우저와 관계없이 스터디당 활성 타이머는1개이며 일시정지도 포함한다. A가 일시정지 중이면 새 B를 시작할 수 없고 A를 재개하거나 초기화한다. 초기화 후에는 원래 설정 시간·경과0의 시작 전으로 돌아가고 Start로 시작한다. 포인트는 초기화·목표 시간 종료 때만 지급하며 일시정지 때는 지급하지 않는다. 경과10분당1P를 정산하고 목표 종료만 추가3P를 지급한다. 초기화 전후 시도와 서로 다른 집중의 10분 미만 나머지는 버리고 기지급 포인트는 유지한다. 기존 상한 해제는 유지한다.
- 이유: 일시정지된 집중도 활성에 포함해야 새 타이머가 기존 경과를 우회하지 않는다. 초기화와 재개를 구분하고 집중 사이의 나머지 시간을 이월하지 않아 각 집중의 계산 범위를 명확하게 한다. 지급 시점은 이후 ADR-053으로 대체됐다.
- 영향: ADR-026·035의 미정 세부를 보완하며 ADR-029의 지급량과 ADR-031의 상한 해제를 유지한다. 초기화 직전 미지급 경과 보상을 먼저 정산한 뒤 경과를0으로 돌린다. 25분 목표에서13분 후 초기화는1P, 다음 시도17분 후 초기화도1P로 합계2P다. 180분 목표 달성은21P다.
- 기술 제안: ChallengeStatus에 READY를 추가하고 초기화된 같은 행의 attemptNumber를 증가시킨다. 활성 의미는 RUNNING/PAUSED지만, READY 재시작에서 행을 재사용하기 위해 READY/RUNNING/PAUSED 현재 슬롯 전체를 스터디당1개로 제한하는 부분 UNIQUE를 제안한다. 최초 Start는201, READY 재사용은200. pause/resume/reset/complete는 attemptNumber를 받아 오래된 시도를 거절한다. 완료 재요청은 신규 지급0으로200, 초기화 전 오래된 요청은409 STALE_ATTEMPT로 처리하는 API 제안이다.
- 정산 전달 제안: 프론트는 목표 종료에 complete를 호출하고, 조회는 지급하지 않는다. 종료 후0초 상태로 복귀하면 complete를 재요청해 복구한다. 서버 요청 없이 정확한 종료 시각에 DB 지급을 보장하는 백그라운드 작업은 도입하지 않는다. 이탈 요청 누락 시 시간 확정·여러 브라우저의 조작권은 별도 미정이다.
- 관련 기능·화면: F-FC-001~012, S-006
- 다시 볼 때: API·DB 초안 승인, 초기화/완료 중복 요청·동시 시작·외부 이탈 복구 구현 시.

| 주제 | 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- | --- |
| 활성 범위 | PAUSED도 포함 | 정지된 타이머의 경과를 이어가며 스터디당1개 유지 | 새 타이머 전에 기존 재개·초기화 필요 | 채택 |
| 활성 범위 | RUNNING만 포함 | 정지된 타이머를 두고 다른 집중 시작 가능 | 여러 미완료 타이머 관리·복귀 선택 필요 | 미채택 |
| 초기화 후 | 시작 전 | 원래 설정 시간에서 Start로 새 시도 시작 | 재개와 시작을 API·화면에서 구분해야 함 | 채택 |
| 초기화 후 | 일시정지로 취급 | 기존 PAUSED 상태 코드 재사용 | 합의한 시작 전 상태와 불일치 | 미채택 |
| 지급 시점 | 초기화·목표 종료만 | 상태 전환과 정산을 함께 처리 | 진행·일시정지 중 누적 표시에는 미정산 보상 제외 | 채택 |
| 지급 시점 | 10분마다 또는 일시정지도 지급 | 중간에 보상 확인 가능 | 지급 트리거·중복 처리 증가 | 미채택 |
| 남은 시간 | 시도·집중마다10분 미만 버림 | 독립된 집중 단위 계산 | 남은 시간이 다음 집중에 이월되지 않음 | 채택 |
| 남은 시간 | 다른 시도·집중과 합산 | 전체 경과에 비례한 보상 가능 | 이월 잔여 시간 저장·초기화 기준 추가 필요 | 미채택 |

## ADR-040 — API·DB 초안 승인과 구현 이슈 작성

- 날짜: 2026-10-10
- 상태: 채택; 이슈 목록은 검토용 초안

- 이유: API·DB 초안을 실제 구현 단위로 나누고 끝났다고 볼 기준을 연결해야 3명이 작업을 분담할 수 있다. 남은 제품 결정은 해당 기능의 완료 조건으로 남기며 문서 검토 완료와 구현 완료를 구분한다.

- 다시 볼 때: 이슈 초안 검토, 담당자·일정 배정 및 미정 정책 확정 시.

## ADR-041 — 다른 브라우저의 활성 타이머 조작 차단

- 날짜: 2026-10-10
- 상태: ADR-051~052로 대체 — 비밀번호를 아는 다른 브라우저 조작 허용
- 결정: DB에서 스터디당 활성 타이머1개를 관리한다. 활성에는 RUNNING과 PAUSED를 포함하며, 다른 브라우저에서 시작·조작을 시도하면 경고 메시지를 표시하고 동작하지 않도록 서버에서도 차단한다.
- 이유: 당시에는 다른 브라우저가 실행 중인 타이머를 임의로 멈추거나 초기화하는 상황을 차단하려 했다. 단일 활성 제약만으로 조작 주체를 구분할 수 없어 소유권·복구 계약이 필요했고, 현재는 이 복잡도를 제외했다.
- 영향: 당시 브라우저 공동 조작안은 미채택이다. Challenge의 소유 브라우저 식별 저장, 요청 식별 전달·서버 비교, 실패 응답·경고 표시가 필요하다. 현재 스키마·api.http에는 이 계약이 완성돼 있지 않으며 ISS-002에서 보완 후 ISS-004·014~019에서 구현·검증한다. 식별자는 비밀번호 검증을 대체하지 않는다.
- 남은 항목: READY/COMPLETED 이후 조작권 수명, 저장소 삭제·닫힌 창의 복구, 소유권 이전 여부와 이탈 요청 누락 처리. 합의 없이 확정하지 않는다.
- 다시 볼 때: ISS-002 계약 보완과 다중 브라우저·동시 요청 검증 시.

| 선택지 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 시작한 브라우저만 활성 타이머 조작 | 다른 브라우저가 진행·정산 상태를 변경하는 것을 차단 | 브라우저 식별 저장과 복구·수명 계약 필요 | 채택 |
| 비밀번호를 아는 브라우저 모두 조작 | 별도 조작권 식별 없이 공동 조작 가능 | 다른 브라우저가 일시정지·초기화 가능 | 미채택 |

## ADR-042 — 15초 연결 확인과 만료 시 자동 일시정지

- 날짜: 2026-10-10
- 상태: ADR-052로 대체 — 연결 확인·연결 만료·자동 일시정지 제외
- 결정: 당시에는 브라우저 종료 정지 요청의 누락을 15초 연결 확인으로 보완했다. 서버가 마지막 확인 시각을 저장하고 유효기간 만료 시 그 시각까지만 경과를 인정해 PAUSED로 복구한다. 타이머·지급 이력은 보존하고 자동 정지에는 지급하지 않는다.
- 이유: 브라우저 종료 요청은 전달되지 않을 수 있으므로 당시에는 마지막 유효 연결 시각으로 정지 상태를 복구하려 했다. 연결 확인은 감지 실패를 보완하지만 네트워크·절전 오차와 추가 요청이 필요해 현재 범위에서는 제거했다.
- 적용 방식: 후속 집중 요청에서 만료를 먼저 검사한다. 요청이 없을 때 DB 상태를 즉시 변경하는 별도 주기 작업은 포함하지 않는다. 늦은 확인은 자동 재개하지 않는다. 다른 브라우저는 확인 연장·조작을 할 수 없다.
- 미정: 만료 대기 시간은15초 확인 간격과 별개다. 이전60초는 예시이며 확정하지 않는다. 브라우저 식별·조작권 수명·탭 전환/최소화·내부 이동 중 보호 요청의 메모리 비밀번호 전달 구조는 ISS-002에서 보완한다.
- 영향: Challenge.lastHeartbeatAt 추가, API-FC-07 연결 확인 계약 및 api.http 예시 추가. 단일 활성·Cascade·초기화/완료 정산 정책은 유지한다. 네트워크 단절·백그라운드 제한도 정지로 판단될 수 있고 마지막 확인 이후 시간은 일부 인정되지 않을 수 있다.
- 다시 볼 때: 만료 대기 시간 확정, 이탈·네트워크 단절·목표 경계 검증 시.

## ADR-043 — 일반 인증 토큰·한국 자정 만료와 타이머 키 분리

- 날짜: 2026-10-10
- 상태: ADR-051~052로 대체 — 일반 토큰·타이머 전용 키·자정 만료 제외
- 결정: 기존 매 요청 비밀번호 방식을 일반 토큰으로 변경한다. 스터디별 LocalStorage 보관·내부 공유·새로고침/재접속 유지, 다음 한국 자정 서버 만료를 적용한다. 타이머는 별도 키로 자정 이후에도 진행·정지·재개·정산 가능하며 새 시작·습관·수정은 일반 토큰이 필요하다. 삭제는 기존 모달의 비밀번호 재확인 유지.
- 이유: 당시에는 내부 이동 중 비밀번호 폐기와 Heartbeat 인증 충돌을 풀기 위해 일반 토큰과 타이머 키를 분리했다. 반복 bcrypt 비용을 줄일 수 있지만 키 보관·복구·자정 만료를 추가로 관리해야 하므로 ADR-051~052에서 대체했다.
- 기술 계약: 토큰 서명은 Node 내장crypto·HMAC-SHA256 기술 설계, VerificationToken 테이블 없음. 타이머 키는32바이트 난수·DB SHA-256 해시·LocalStorage 원문. 분실 시 비밀번호 재확인과 명시적 복구로 교체·이전 키 무효화. RESET/COMPLETED에서 폐기. 일반 토큰 만료가 타이머 키를 무효화하지 않는다.
- 영향·대체: ADR-038의 반복 비밀번호·페이지별 재입력과 ADR-041의 미정 식별을 대체한다.당시 보관 위치와 만료 기준은 LocalStorage·한국 자정으로 정리했다. Heartbeat15초 유지·만료 대기 시간 미정. 키 공유는 브라우저 프로필 단위이며 영구 개인 인증이 아니다.
- 다시 볼 때: 토큰·복구 API 구현, 자정·다중 브라우저·키 분실 검증 시

## ADR-044 — RESET 종료·새 집중 행과 포인트 총점 저장

- 날짜: 2026-10-10
- 상태: 새 행·총점 저장 유지(ADR-052~053); PointHistory·초기화 지급 제외
- 결정: 초기화는 PAUSED의 기존 행 경과 보상을 정산하고 RESET으로 종료한다. 다음 Start에서 새 행·새 키를 만든다. 기존 목표는 가장 최근 종료 행에서 복원한다. Study.points를 두고 PointHistory 신규 지급과 같은 트랜잭션으로 증가시킨다. 목표 초과분 제외·초기화/완료만 지급·완료 추가3P·나머지 버림·상한 해제는 유지한다.
- 이유: 집중 1회를 행 1개로 남기면 초기화 전후 시도를 구분하기 쉽고 최근 목표를 복원할 수 있다. Study.points는 정렬·목록 조회에 사용하되 지급 근거와 같은 트랜잭션으로 갱신해야 한다. 별도 원장은 현재 awardedPoints로 축소했다.
- 기술 계약: READY·attemptNumber 제거, 종료 시각 endedAt 도입. 활성 부분 UNIQUE는RUNNING/PAUSED만. PointHistory PK는challengeId/kind/sequence. 종료 중복 요청은 신규0P, 키 폐기 후 동일 종료 재확인은 일반 토큰 필요.
- 영향·대체: ADR-039의 READY 재사용 기술안을 대체한다. 기존 데이터가 있으면 변환 계획 필요하며 이번에 DB 적용하지 않는다. 원장·총점 불일치 방지를 위한 잠금·원자 증가·롤백이 필수다.
- 다시 볼 때: migration·동시 정산·장애 롤백·새로고침 목표 복원 검증 시

## ADR-045 — 습관 종료일 포함·주간 겹침·검색과 조회 정책

- 날짜: 2026-10-10
- 상태: 채택; 명시한 미정과 기술 계약은 구분
- 결정: 습관 기록의 startsOn/endsOn은 양끝 포함. 종료 즉시 목록 숨김·조작 차단, 종료 당일 기록 보존. 주간 표에는 사용 기간이 조회 주와 겹치는 습관만 표시한다. 습관 이름 최대20글자, 검색 대상은스터디 이름/닉네임/소개. 최근 ID 다건 조회 API 추가. 응원 정렬은개수내림→최초반응시각오름→이모지값오름.
- 이유: 종료 당일을 제외하면 당일 체크 후 삭제한 기록이 사라진다. 종료일 포함과 조회 주 겹침 조건을 함께 사용해 기록을 보존하면서 오래된 종료 습관의 빈 행이 계속 표시되는 것을 막는다. 검색·반응 동률 기준도 공통으로 고정한다.
- 기술 계약: 이름은Routine에서조회해과거표에도최신값반영. 체크해제false행보존. ST-08은입력ID순서유지·삭제ID제외, 부분검색OR·동률이모지C정렬·3종미만있는만큼은기술계약으로명시한다.
- 영향·대체: 기존 종료일 배타 기준과 API 미정 검색/응원동률을 대체한다. 공백·글자 계산·이모지 동일성·다건상한·기본주·습관18개 범위는 미정으로 남긴다.
- 다시 볼 때: 습관 당일 종료·주 변경·검색/응원 경계 검증 시

## ADR-047 — 90초 연결 만료·새로고침 유지·여러 탭 인계

- 날짜: 2026-10-10
- 상태: ADR-052로 대체 — 90초 만료·Heartbeat·담당 탭 인계 제외
- 결정:15초 연결 확인은 유지하고 마지막 확인 후90초 이상이면 만료한다. 종료 이벤트에서pause를 보내지 않는다. 새로고침은90초 이내 진행 유지, 만료 뒤에는PAUSED·수동 재개. 같은 브라우저 프로필의 담당 탭 하나만 주기 확인하며 보조 탭 종료는 영향 없다. 담당 탭 종료/새로고침/응답 중단은 다른 열린 탭이 인계한다.
- 이유: 당시 90초 유예는 일시적인 확인 누락과 실제 이탈을 구분하기 위한 절충이었다. 담당 탭 인계는 여러 탭에서 학습하는 흐름을 유지할 수 있지만 탭 간 조정과 실기기 지연 검증이 늘어나 현재는 제외했다.
- 영향: 모든 사이트 탭의 확인이 끊기면 마지막 확인 시각까지만 경과 인정·무지급 정지. 다른 탭이 연결을 유지하면 담당 탭 외부 이동에도 진행한다. 이전 reason=leave 계약과 ‘만료 시간 미정’을 대체한다. 요청 없는 동안DB변경은 지연될 수 있으나 다음 요청 전에 복구한다.
- 기술 계약: 담당 선정은 브라우저 내부 통신/임대, DB 탭 테이블은 추가하지 않는다. 인계 중 잠깐 중복heartbeat는 허용하고 경과/포인트 중복가산 금지. 다른 브라우저 조작 차단과 명시적 복구는 유지한다.
- 한계: 백그라운드 제한·절전·통신 단절에서90초 확인이 끊기면 정지할 수 있다. 모든 환경에서 무중단 진행을 보장하지 않는다.
- 다시 볼 때: 실제 PC/모바일 지연·새로고침·다중 탭 인수 검증 시.

## ADR-048 — 오래된 요청·습관 경합·포인트 문서 보완

- 날짜: 2026-10-10
- 상태: 집중 stateVersion·PointHistory 보완은 ADR-052~053으로 대체; 습관 쓰기 무결성 유지
- 결정: Challenge.stateVersion을 도입해 실제 상태 전환·자동 만료·키 복구마다 증가시키고 조작/heartbeat의 과거 버전을 거절한다. 습관 체크·수정·종료는 Study→Routine 잠금 순서로 원자적으로 처리한다. PointHistory.kind/sequence를ERD·데이터 사전에 복원한다.
- 이유: 늦게 도착한 요청이 재개 구간을 바꾸는 문제와 종료 검사 뒤 습관 체크가 저장되는 문제를 분리해 다뤘다. 현재 집중의 버전 관리는 제외하지만 습관 쓰기 원자성과 완료 중복 지급 방지는 데이터 무결성의 기본 조건으로 유지한다.
- 영향: FC-03~07의 활성 키 요청은stateVersion필수,409 STALE_FOCUS_STATE추가. heartbeat자체는버전증가없음. 만료를 발견한heartbeat는200 PAUSED, terminal일반토큰재확인은기존신규0P예외유지. 생성·초기화의새행정책은변경없다.
- 다시 볼 때: 요청역순·자동만료·탭인계·체크/종료동시성검증 시.

## ADR-051 — 토큰 제거와 페이지별·요청별 비밀번호 검증

- 날짜: 2026-10-12
- 상태: 채택
- 결정: 일반 인증 토큰·타이머 전용 키·자정 만료·LocalStorage 인증을 제거한다. 습관·집중·수정 페이지마다 API로 비밀번호를 확인하며 페이지 메모리에만 보관한다. 이탈·새로고침 후 다시 입력한다.
- 전달 계약: 보호 API는 X-Study-Password 헤더로 비밀번호를 전달한다. 페이지 진입 검증과 삭제 모달은 본문 {password}, 생성은 기존 비밀번호/확인 본문을 유지한다. 서버는 요청마다 bcrypt로 확인한다. 검증 응답 {data:{verified:true}}는 이후 요청의 권한 증표가 아니다.
- 이유: 10/14 구현 목표에 맞춰 토큰 발급·서명·보관·만료·타이머 키 복구를 제거하고 bcrypt 검증 경로 하나로 보호 요청을 처리한다. 헤더는 GET 조회와 변경 요청에 같은 방식으로 적용할 수 있다. 반복 검증 비용과 페이지 메모리의 비밀번호 보관은 감수하되 HTTPS·로그 제외·이탈 시 폐기를 함께 적용한다.
- 영향: 비밀번호 원문을 LocalStorage·쿠키·URL·응답·로그에 남기지 않는다. HTTPS와 해당 헤더 CORS 허용·민감 로그 제외가 필요하다. 토큰/키 실패 코드와 API-AU-02 조작권 복구는 제거한다.
- 대체: ADR-043의 인증 정책. ADR-038의 페이지별/요청별 검증 방향을 현재 계약으로 재확정한다.

| 방식 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 보호 요청 공통 비밀번호 헤더 | GET 조회와 변경 요청에 공통 적용, 기존 API 메서드 유지 | 헤더 읽기·CORS·민감 로그 제외 필요 | 채택 |

## ADR-052 — Challenge 축소와 브라우저 종료 후 계속 진행

- 날짜: 2026-10-12
- 상태: 채택
- 결정: 시작·일시정지·재개·초기화·완료·서버 시간 복원은 유지한다. Challenge를 id, studyId, goalMinutes, status, elapsedMilliseconds, lastStartedAt, awardedPoints, createdAt의 8개 컬럼으로 축소한다.
- 상태 값: RUNNING/PAUSED/RESET/COMPLETED를 사용한다. RUNNING/PAUSED 합계는 스터디당 1개다. 일시정지된 집중이 있으면 새 집중 대신 재개/초기화를 해야 한다.
- 시간: elapsedMilliseconds는 이전 실행 구간의 누적이고 lastStartedAt은 현재 구간의 시작 시각이다. RUNNING만 서버 현재 시각 차를 더하며 목표 길이로 제한한다. 정지 시간은 제외한다.
- 초기화: PAUSED에서만 RESET으로 종료하고 행은 보존한다. 지급 없음, 화면은 원래 목표·경과 0의 시작 전 상태. 다음 Start에서 새 행을 만든다.
- 제외: 토큰·타이머 키·소유권·연결 확인·연결 만료·자동 일시정지·담당 탭 인계·stateVersion. 브라우저 종료·외부 이동에도 RUNNING은 서버 시간으로 흐른다. PAUSED는 그대로다.
- 브라우저: 비밀번호를 아는 다른 브라우저는 같은 집중 조작 가능. 여러 브라우저 요청 순서 충돌 처리는 제외하지만 스터디당 단일 활성과 완료 중복 지급 방지는 유지한다.
- 이유: 수동 정지·재개와 새로고침 복원에 필요한 것은 확정된 경과와 현재 실행 시작 시각이다. 이 두 값을 유지하고 소유권·Heartbeat·자동 정지·버전을 제외해 시간 계산과 검증 범위를 줄인다. 브라우저 종료 뒤에도 서버 시간으로 진행하는 정책을 명시해 종료 감지의 신뢰성 문제를 없애고, 단일 활성 제약은 유지한다.
- 영향: Challenge의 timerKeyHash, lastHeartbeatAt, stateVersion, endedAt, updatedAt을 제거한다. API-FC-07·API-AU-02를 폐기하고 ID는 재사용하지 않는다. 창을 닫은 동안 목표를 채운 경우 복귀 후 비밀번호 확인·완료 요청으로 지급한다. 조회는 지급/종료를 수행하지 않는다.
- 대체: ADR-007·041~043·047 및 ADR-048의 집중 버전 정책. 내부 이동·새로고침 서버 복원, 활성 1개, RESET 새 행은 유지한다.

## ADR-054 — DB와 API의 도메인 용어 통일

- 날짜: 2026-10-12
- 상태: 채택
- 배경: 같은 데이터를 DB와 API에서 서로 다른 이름으로 다뤄 프론트·서버 간 변환과 계약 확인이 필요했다.
- 결정: 리소스명은 Routine·RoutineHistory·Challenge·Reaction을 기준으로 한다. JSON 필드는 DB 컬럼과 같은 camelCase, 컬렉션 경로는 복수형·kebab-case로 작성한다. 현재 집중 조회는 /studies/{studyId}/challenges/current다.
- 이유: 같은 개념에 여러 이름을 사용하면 요청·응답 필드를 잘못 연결하거나 문서마다 다른 이름으로 구현하기 쉽다. DB 명칭을 공통 기준으로 삼아 변환 코드를 줄이고, API 예시·테이블·이슈 완료 조건을 함께 대조할 수 있게 한다.
- 영향: API v0.9의 경로·필드·실패 코드를 적용하고 이전 별칭은 지원하지 않는다. elapsedSeconds·remainingSeconds 등 파생값은 DB 저장 컬럼과 구별한다. 기존 기능/API 추적 ID와 6개 화면 주소, DB 모델·관계는 유지한다.
- 시간 응답: Challenge의 elapsedMilliseconds·lastStartedAt·createdAt을 같은 이름과 의미로 전달하고, 현재 실제 경과 초는 elapsedSeconds로 별도 계산한다. 저장 누적값을 조회 시 계산한 값으로 덮어쓰지 않는다.

## ADR-055 — 중간점검을 CR 중심 API 흐름 시연으로 재편

- 날짜: 2026-10-12
- 상태: 채택
- 결정: 10/13~15 구현, 10/16 중간 발표. 프론트 없이 `api/requests/api.http`로 API 흐름을 연결한다.
- Must/P0: Express·Prisma·PostgreSQL 연결·migration, 스터디 생성→목록→상세, 습관 생성→오늘 조회→체크→주간 기록, 집중 시작→상태→완료→포인트 조회, HTTP 시연 순서·변수·예상 응답.
- Should/P1: 공통 응답·오류·입력 검증, 비밀번호 확인·보호 요청 검증, 완료 조건 서버 검증·중복 지급 방지.
- Could/P2: 검색·정렬·더보기·스터디 ID 다건 조회·응원 등록·상위 반응 조회.
- 이유: 실제 DB 저장·조회를 기반으로 앞 요청에서 얻은 ID를 후속 요청에 사용하고, 습관 기록과 집중 포인트까지 연결되는 흐름을 중간점검에서 보여주기 위함이다. CR 중심으로 작업하며 프론트는 고려하지 않는다.

## ADR-056 — 습관 최대 개수·공백·그래핌·목록 순서

- 날짜: 2026-10-13
- 상태: 채택
- 결정: 스터디당 최대18개는 endsOn=null인 습관만 센다. 종료된 습관과 날짜별 기록은 개수에서 제외한다. Study 잠금 안에서 count → create를 처리하고 초과 시 기존 400 VALIDATION_ERROR로 응답한다.
- 결정: 이름은 trim()으로 앞뒤 공백을 제거한 뒤 Intl.Segmenter("ko", {granularity:"grapheme"})로 1~20글자인지 검사한다. 빈 문자열·공백만 있는 이름은 거절하고 정리한 값을 저장한다. 조합 이모지도 각각 1글자로 세며 Routine.name은 TEXT로 저장한다.
- 결정: 오늘 습관 목록은 기존 생성일 오름차순(createdAt ASC → id ASC)을 유지한다. 추후 드래그앤드롭으로 순서를 변경할 수 있게 한다. 현재 순서 컬럼·변경 API는 추가하지 않으며 ISS-031에서 후속 설계한다.
- 이유(그래핌): 보이는 글자 수를 20자로 유지해 사용자에게 의문을 주지 않기 위함이다. JavaScript 내장 기능이므로 추가 라이브러리가 필요 없고 조합 이모지도 각각 1글자로 센다. VARCHAR는 조합 이모지를 여러 문자로 계산하므로 저장 타입 변경이 필요하다.
- 이유(개수·공백·정렬):
- 영향: API-Q-06의 습관 관련 미정을 해소한다. 기존 종료일 포함·과거 기록 보존 정책은 유지한다. 생성·수정·프론트 입력에 같은 이름 규칙을 적용하고 DB 변경은 후속 migration으로 반영한다.
- 대체: ADR-045~046에 남겼던 습관18개 적용 범위·공백·글자 수 미정을 대체한다. 기존 최대20글자 요구는 유지하고 계산 단위를 명확히 한다.
- 다시 볼 때: 드래그앤드롭 순서 변경을 도입할 때.

## ADR-057 — 스터디 문자열·임시 배경 키·비밀번호 공백

- 날짜: 2026-10-13
- 상태: 일반 문자열·배경은 채택 유지; 비밀번호 공백 거절은 ADR-062로 대체
- 결정: 닉네임·스터디 이름·소개는 trim 후 빈 문자열을 거절하고 그래핌 기준 1~10·1~15·1~100글자를 허용한다. 습관과 같은 Intl.Segmenter 기준을 쓰며 Study의 세 컬럼은 TEXT로 저장한다.
- 결정: 기본 배경 green과 총8종(원색4·이미지4)을 유지한다. 담당자가 나머지7종 임시 키·자산을 지정해 프론트·서버에 공유하고 추후 변경한다. 구체 키를 이 ADR에서 임의로 고정하지 않는다.
- 결정: 비밀번호·확인값의 앞뒤·중간 공백을 모두 금지한다. 프론트에서 공백 입력을 막고 서버에서 원문을 검사한다. trim·공백 제거로 입력을 바꾸지 않는다. 기존 `/^[A-Za-z0-9!@#$%^&*]+$/`는 공백을 허용하지 않으므로 유지한다. 4~20자·확인값 일치·bcrypt 해시 저장·비밀번호 변경 제외는 유지한다.
- 이유(그래핌): ADR-056과 같은 보이는 글자 수 기준을 적용한다.
- 이유(배경·공백):
- 영향: 스터디 생성·수정과 모든 비밀번호 입력에 공통 검증 기준을 적용한다. 임시 배경 목록 밖 키는 400 INVALID_BACKGROUND로 거절한다. TEXT 변경 migration·공통 입력 함수·프론트 검증·배경 목록 공유는 후속 구현 작업이며 이번 명세 변경으로 구현 완료를 뜻하지 않는다.
- 대체: ADR-015·045~046의 스터디 문자열 계산 미정과 나머지 배경 키 수신 전 구현 보류 기준을 보완한다. backgroundKey 필드명과 green 기본값은 유지한다.
- 다시 볼 때: 배경 키를 추후 변경할 때.

## ADR-060 — 현재 코드 기준 주간 기록 계약

## ADR-062 — 프론트·서버의 비밀번호 공백 제거

- 날짜: 2026-10-15
- 상태: 채택
- 결정: 프론트 공백 입력 방지와 별도로 프론트·서버에서 비밀번호·확인값의 모든 공백을 제거한다. 범위는 JavaScript /\s/gu이며 앞뒤·중간 스페이스·탭·줄바꿈 등을 포함한다. 정리 후4~20자·기존 허용 문자 정규식을 검사한다.
- 결정: 생성은 정리된 두 값의 일치를 확인하고 정리된 password만 bcrypt 해시로 저장한다. 진입 확인·삭제·모든 보호 요청도 공백 제거 후 bcrypt 비교한다. ab cd와 abcd는 같은 비밀번호다. 비문자열을 자동 변환하지 않는다. 제거 후 빈 값/형식 오류·생성 필수 필드 누락은400, 진입 확인·삭제·보호 요청의 비밀번호 누락은 기존401, 유효 형식의 오답은401로 구분한다.
- 이유:
- 영향: 생성 스키마·공통 검증 서비스·프론트 입력의 후속 수정이 필요하다. 이번에는 문서와 요청 예시만 갱신하며 코드 변경·DB 재해시는 수행하지 않는다. 비밀번호 변경 API는 추가하지 않는다.
- 대체: ADR-057의 비밀번호 원문 공백 거절·공백 제거 금지를 대체한다. 일반 문자열 trim·그래핌 규칙, 요청별 비밀번호 헤더·토큰 미사용·bcrypt 저장은 유지한다.
- 다시 볼 때:

| 선택지 | 장점 | 비용 | 선택 |
| --- | --- | --- | --- |
| 프론트·서버 모두 공백 제거 | 공백 위치에 관계없이 같은 정리 기준 적용 | 공백을 포함해 다른 원문도 같은 비밀번호로 처리 | 채택 |
| 프론트만 제거·서버는 거절 | 서버는 받은 문자열을 그대로 검사 | 직접 API 요청과 프론트 처리 기준이 달라짐 | 미채택 |

## ADR-063 — 다건 조회는 중복 제거 후 최대10개

- 날짜: 2026-10-15
- 상태: 채택
- 결정: ST-08은 UUID 형식을 검사하고 첫 등장 순서로 중복을 제거한 뒤 서로 다른 ID를 최대10개까지 허용한다.11개 이상은 400 VALIDATION_ERROR다. 없는/삭제된 ID를 DB 조회 결과에서 제외하기 전에 상한을 검사한다.
- 결정: 원래 요청 항목이10개를 넘어도 중복 제거 후10개 이하면 허용한다. 조회 결과는 첫 등장 순서·없는/삭제된 ID 제외를 유지한다. 최근 조회 UI 표시 개수와 목록limit 최댓값은 별도다.
- 이유:
- 영향: 다건 전용 라우트·입력 검증·10/11개 경계 요청을 후속 구현한다. 이번에는 명세만 갱신하며 구현 완료로 표시하지 않는다.
- 대체: API-Q-04의 다건 조회 개수 상한 미정을 해소한다.
- 다시 볼 때:

| 선택지 | 장점 | 비용 | 선택 |
| --- | --- | --- | --- |
| 중복 제거 후10개 | 실제 서로 다른 조회 대상을 제한 | 원본 요청 항목 수는 이 규칙으로 제한하지 않음 | 채택 |
| 중복 제거 전10개 | 원본 항목 수 기준이 단순 | 같은 ID 반복도 한도를 소모 | 미채택 |
